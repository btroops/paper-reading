# "Skill Issues": Data-Centric Optimization of Lakehouse Agents

## Why

编码 agent 正在成为数据基础设施的使用者，但它们能不能把事做成，不只取决于模型。论文的出发点是一个运维事实：平台方给用户发一套 Markdown 文件（论文叫 **skill**，技能文档）加一份 `CLAUDE.md`，告诉 agent 这个平台怎么用、代码怎么写、怎么测、怎么发版。这套文本不是提示词工程的小技巧，而是**系统控制面的一部分**——agent 读它决定调哪个命令、走哪条分支、什么时候该停下（§1）。既然如此，它就该像代码一样被优化和评测。

手工维护这套文本不可持续，原因有三条，都在机制层。第一，客户选的模型、编码助手、使用方式在几个月内就换了一轮，一套写给某个模型看的技能文档，换个模型就可能失效；靠人读反馈改，跟不上这个节奏。第二，技能文档的失效方式很隐蔽：agent 不是"不会用这个 API"，而是"用了一个不存在的参数""跳过了必须的校验分支""在只读任务里跑了会写数据的命令"，这些都要看轨迹才能发现。第三，改一版技能之后，怎么知道改好了？如果评测只看最终回答，一个把数据改坏的 agent 也可能因为解释得漂亮而拿高分。

已有的做法在这三点上各有缺口。一般的提示词优化工作在通用任务上做（软件工程、问答、数学、网页导航、工具调用），优化的对象是任务提示词，评测靠答案匹配或 LLM 裁判（§5）。数据工程场景不一样：任务的产物不是一段文字，而是**数据状态的改变**——建了哪张表、写了哪些行、提交在哪个分支上。用答案匹配去评这类任务，等于放弃了唯一可靠的信号。另一类做法是合成可执行基准（SWE-bench 式），但那些基准的可执行对象是源码补丁；在数据平台上，可执行对象是一串带副作用的操作，效果落在分支、提交、表、模式、行与合并上（§3.2.2）。

为什么现在必须解决：论文给出的理由来自生产日志。2026 年 5 月的一份匿名采样显示，计算类 API 的使用分布是导入 40%、查询 35%、运行流水线 25%；分支类 API 是合并 43%、删除 37%、创建 11%、查询详情 8%、列举 1%（Table 2）。也就是说，真实负载里超过一半是**写路径**——导入、跑流水线、合并、删分支。写路径出错不是"答案不对"，而是数据被改坏。而现有评测大多停在只读路径（text-to-SQL、数据探索），写路径基本没有可靠的自动判分方式（§1）。

于是问题落到这里：能不能把"技能文档"当成待优化的参数，用**可程序化验证的数据状态变化**当奖励，在隔离沙箱里反复试、自动改进？如果能，改好的技能在一个没参与优化的留出集上还成立吗？改进的幅度有多大，代价是什么？

## What

论文的答案是：能，而且改进在留出集上成立。做法是一条数据中心（data-centric）的优化流水线：用 LLM 生成"任务—验证器"配对，在隔离沙箱里用当前技能跑 agent，从三个层次打分（工具轨迹、湖仓状态、回复质量），把分数与错误轨迹交给 GEPA 生成新的技能文本，循环往复（Fig. 3）。在 780 道题的基准上，六个技能里的每一个都在留出集上变好，平均提升 12.0%，最高 28.6%（§4）。

先把任务说清楚。输入是一份技能文档（Markdown 文本）与一批基准题；每道题包含一句用户请求、一份初始湖仓状态、一组期望的平台交互、一组禁止动作、以及一段程序化验证脚本。agent 在一个以它的用户名命名的可写分支上工作，可以调命令行或 Python SDK。输出有两个：这道题的奖励（通过检查的比例，0 到 1），以及优化后的技能文本。边界是 Bauplan 这一个平台、`claude-sonnet-4-6` 这一个模型加 Claude Code 这一个助手；不含跨平台迁移，也不含多技能联合优化。

### 新认识：写路径让评测从"输出匹配"变成"状态验证"

第一个认识改变的是评测对象。在只读任务上，agent 的产物是一段回答，判分只能靠字符串匹配或裁判；在写路径任务上，agent 的产物是湖仓里可观察的变化。论文把这件事叫**代码—数据同构**（code-data isomorphism）：任何读过一段流水线代码的人，都应该能列出"跑成功之后湖仓会变成什么样"——这份代码会创建哪些表、替换还是追加、最终哪个快照被更新（§2.2、Fig. 2）。于是判分可以写成"逐个提交比对状态"，而不是"看 agent 说了什么"。`[已验证：§2.2 的形式论证 + Fig. 2 的一次运行示例]`

第二个认识关于"能不能验证"取决于平台的形状。论文点名两个特性：**无头**（所有交互都走 API，被命令行与 Python SDK 包了一层）与**数据版 Git**（提交、分支、合并这些原语被实现在数据资产上）。前者让验证器能用 agent 用的同一套方法写；后者让"一次运行对应一次提交"成为确定性的映射。没有这两条，写路径的自动判分就退化成"抽样看几张表"。`[宣称，由平台作者提出；这一条同时是利益相关的来源，见 Ideas 第六条]`

第三个认识关于参考分布怎么用。生产日志里的 API 频次能告诉你哪些操作常见，但不能直接当题目配比。论文给了两条理由：轨迹本身被当前技能塑形，写得好的 API 被过度使用、写得差的被低估；而某些罕见操作在安全上极其重要，必须按构造覆盖（§3.2.1）。因此频次只当"概念先验"，最终配比由人在其上调整。这条认识对做数据类基准的人有直接用处：**频次不等于重要性**。`[已验证：Table 2 的分布 + §3.2.1 的说明]`

### 新方法：任务—验证器配对、三层判分、文本进化

第一样方法是**任务—验证器配对**。每道基准题不只有一句请求，还带初始状态、期望交互、禁止动作、回复层检查、可执行验证脚本（§3.2）。生成流程是：给一个场景与角色分类（数据摄取、报表构建、流水线调试；数据工程师、数据科学家、数据分析师），让 LLM 通过结构化工具调用一次生成一条；每条先做语法校验，再过一组语义检查，例如命令必须是真实存在的命令行参数、只读类任务必须至少有一条"阻止写入"的禁止动作和一条"状态未变"的断言。不合格就重采样，直到凑够数量（§3.2.1）。`[§3.2.1]`

第二样方法是**三层判分**。第一层看轨迹：有没有用到期望的技能与命令、有没有触发禁止动作；期望操作同时匹配命令行调用与 Python 脚本（做了命令行到 SDK 的语法转换），多数情况下允许 agent 在两者之间自由选择、不扣分。第二层看湖仓状态：分支是否存在、该变的有没有变、不该变的有没有变，复杂检查逐个提交比对。第三层看回复：硬约束（字符串匹配、正则）加软约束（rubric 形式的 LLM 判分，检查回答是否覆盖要求的维度、是否给出正确的限制条件）（§3.2.2）。奖励是"通过检查的比例"，0 到 1。`[§3.2.2]`

第三样方法是**文本进化**。优化器是 GEPA（Optimize Anything），输入三样：种子技能、评测函数、目标描述。评测函数拿一个候选技能，在相关任务上跑沙箱 agent，按上面的三层判分给 0 到 1 的奖励，连同错误轨迹一起交回；GEPA 据此生成新候选，循环继续（§3.3）。架构是模块化的：只要守住接口，换优化算法不动其它部分。`[§3.3]`

第四样方法是**任务生命周期标准化**。每道题都走同一条六步：从主分支拉出该用户的可写分支、按数据集要求删掉"必须不存在"的表、快照主分支与用户分支的最新提交作为基线、跑 agent、按 `end_conditions` 判分、拆除基线之后产生的所有用户分支并删掉用户主分支（Table 1）。固定生命周期是同一套循环能同时安全评测只读与写路径的原因：写路径的副作用被限制在一个可丢弃的分支上。`[Table 1]`

### 新结论：每个技能都变好，但幅度与代价要分开看

**主结论。** 六个技能（`bauplan-data-pipeline`、`bauplan-safe-ingestion`、`bauplan-data-quality-checks`、`bauplan-data-assessment`、`bauplan-explore-data`、`bauplan-debug-and-fix-pipeline`）在留出集上的奖励都高于种子技能，平均 +12.0%，摘要与引言写"最高 28.6%"。`[宣称；28.6% 对应哪个技能，正文没有点名，只给在 Fig. 4 的曲线上]`

**改进的形态。** 优化后的技能平均比种子长 27.2 倍（按字符数）。改动的内容是"加细节"：加上指向文档的指针、加上"不要自己发明或猜参数"这类句子、加上通用最佳实践（例如在隔离分支上做写入—审计—发布）。`[已验证：§4]`

**失败的地方。** 提升很小的那几个技能，对应的是**多技能任务**——解一道题要同时用对几个技能。论文据此把"联合优化技能"列为下一步工作：现在的做法是逐个技能独立优化，任务集虽然支持需要多技能协作的复杂任务，但优化器看不到这一层。`[已验证：§4 末]`

**数据集。** 780 道题：只读 365 道（探索 139、评估 126、数据质量检查 100），写路径 415 道（新流水线 209、修表 100、摄取 106）（Table 3）。每个技能从题库里抽出"需要该技能"的题，按 70/15/15 切成训练、验证、留出三份；GEPA 在训练集上反思与变异，用验证集挑最优候选，留出集只用于最终报告（§4）。`[已验证]`

## How

判型：以**系统与算法类**为主，附**实证与基准类**。系统与算法类指的是四样可复用的装置：任务—验证器配对的生成流程、带固定生命周期的沙箱、三层判分、以及把技能文本接进优化器的接口。实证与基准类指的是 780 道题的数据集与六个技能的优化曲线。判型依据是核心贡献是"怎么把有状态任务变得可优化、可验证"，不是提出新的优化算法（GEPA 是现成的）、也不是提出新的模型。

### 一、平台形状决定了可验证性

Bauplan 把存储（S3 上的 Iceberg 表）与计算（SQL 与 Python）分开，用户只写逻辑，物理操作发生在平台侧。两个特性直接支撑了验证：

**无头**。所有交互都是 API，被命令行（Bash 场景）与 Python SDK（脚本场景）包了一层。对 agent 来说，它可以用两种方式做同一件事；对验证器来说，它可以用 agent 的同一套方法去读状态。

**数据版 Git**。提交、分支、合并被实现在数据资产上。一次成功运行会在数据分支上产生提交，每次写入对应一个不可变引用；合并到主分支时只原子地更新目标表的快照（Fig. 2）。这就是"代码—数据同构"的落点：一份一节点的 DAG 跑成功之后，湖仓的变化是可枚举的，因此可以逐提交核对。

### 二、一道题的一生：六步，全部可回滚

| 步骤 | 做什么 |
| --- | --- |
| 1 | 从主分支拉出 `<username>.main` 作为 agent 的可写分支 |
| 2 | 准备初始状态：删掉数据集里明确要求"不存在"的表 |
| 3 | 记录基线：快照主分支与用户分支的最新提交 |
| 4 | 跑 agent：把用户请求交给 agent，允许它调命令行与 SDK |
| 5 | 验证：按数据集的 `end_conditions` 打分 |
| 6 | 拆除：删掉基线之后产生的所有用户分支，再删掉用户主分支 |

第 5 步的验证脚本不是写死的字符串：写路径任务的终态依赖用户名，脚本用 SDK 动态发现用户名再断言目标状态（§3.2.2）。第 6 步保证两次尝试之间不残留副作用——这一点与重复测量关系不大（论文每个技能只跑一遍优化），但与"训练与评测共用沙箱"关系很大。

### 三、三层判分各自的用途与各自的漏洞

**轨迹层**查的是"有没有按期望的方式做"：用了哪些技能、调了哪些命令、有没有碰禁止动作。这一层的好处是能给出细粒度反馈（"你没有先用 `bauplan branch create`"），让优化器知道该改哪句话。坏处是它是**过程匹配**：命令对了、参数对了，不代表状态对。所以它只能当分量，不能当主判据。

**状态层**查的是"湖仓变成了什么样"：分支是否存在、该变的变了没有、不该变的变了没有，复杂检查逐个提交比对。这一层是主判据，也是"状态验证"这个说法真正的依据。

**回复层**只对不改变状态、也没有结构化输出的任务用，典型是数据探索：这类任务以一段自由文本结束。判分是硬约束（字符串、正则）加软约束（rubric 形式的 LLM 判分）。

三层合起来的奖励是"通过检查的比例"。这个设计的好处是信号密（不是全 0 或全 1），代价是它给了过程匹配权重——见 Ideas 第三条。

### 四、数据生成：先验、分类轴与校验

生成器的输入是三样：场景与角色分类、平台专有上下文（技能、SDK、命令行文档）、可用数据集。对摄取类任务，提示词里直接给 S3 URI；其它任务则声明预先加载了哪些表。每条生成结果先做语法校验，再做语义检查，例如命令必须是真实存在的参数；只读类任务必须至少有一条阻止写入的禁止动作、一条"状态未变"的断言，防止只读任务偷偷允许破坏性操作（§3.2.1）。

分类轴有两个。第一个是**工作类型**：只读（数据探索、text-to-SQL、数据管理检查）与写路径（安全摄取、新流水线、加期望、改/调试流水线、分支操作、端到端分析）。第二个是**请求的具体程度**：模糊提示对应新手用户，中等对应普通从业者，详细对应会指定表、列、输出模式与验收标准的专家用户。这条轴是论文相对既有合成数据方法（按"深度"细化意图、按"覆盖"扩展变体）的增量：它加了一个**用户侧维度**（§3.2.1）。

### 五、优化：GEPA 看到什么

GEPA 的输入是种子技能、评测函数、目标描述。评测函数做四件事：把候选技能写进沙箱的技能目录，挑出"需要这个技能"的训练题，跑 agent，算奖励，把奖励与错误轨迹一起返回。GEPA 用这些反馈反思并改写技能文本，生成新候选；验证集用来在候选之间挑，留出集不参与挑选（§3.3、§4）。

一个具体例子能说明它改的是什么。种子技能可能只写"用 `bauplan run` 跑流水线"；优化后可能写"先在隔离分支上跑，确认 `run_state.success()` 为真再合并；不要自己发明 `--force` 这类参数，参数表见官方文档；如果任务要求保留历史，用追加而不是替换"。这些都是**可检验的操作知识**，不是修辞。

### 六、证据强度

主证据是一张图（Fig. 4），六个子图，每个子图画出候选序号上的验证集与留出集奖励曲线。没有表，没有置信区间，没有多种子。文本给出的数只有三个：平均 +12.0%、最高 28.6%、技能变长 27.2 倍。因此"每个技能都变好"这个结论只能按"曲线在留出集上不低于种子"来理解，不能按"提升 12.0 个百分点"来理解——12.0% 是相对值还是绝对点，正文没写。

### 七、开销与边界

论文没有报告优化成本：每个技能要跑多少候选、每个候选跑多少题、每次运行多少 token、总花费多少，都没有。它报的是产物侧的代价——优化后的技能长度是种子的 27.2 倍。这个数在生产里直接对应上下文占用：一个技能从约 1,000 字符涨到 27,000 字符，如果六个技能都被注入，就是十几万字符的常驻开销（数量级由 27.2 倍推出，论文未给绝对值）。

边界有四个。第一，只有一个模型配置（`claude-sonnet-4-6` + Claude Code），作者自己说"重要但初步"。第二，优化器只看单个技能，多技能任务提升有限。第三，数据集由 LLM 生成、由专家抽样审查，审查的样本量与一致性没报。第四，任务生成在内部用 GPT-5.5 这类前沿闭源模型才做得到"一次成型且内部一致"，代价是高延迟，换成小模型或多 agent 编排留作未来工作。

## Ideas

### 不足

1. **摘要的 28.6% 在正文里无法定位**（评估问题）。摘要与引言都写"最高 28.6%"，正文只说"平均 12.0%"，具体哪个技能达到 28.6%、是相对提升还是绝对点数、对应留出集还是验证集，都没有文字说明，只能去读 Fig. 4 的曲线。对一篇以"方法可复用"为卖点的论文，主结果只以图的形式存在、且没有置信区间，是可复现性的硬伤。

2. **技能变长 27.2 倍没有被计入代价**（方法与评估错配）。奖励只算"通过检查的比例"，没有 token 成本项。优化器面对的激励是"加更多细节能过更多检查"，于是它把技能写到 27 倍长。在生产里这意味着每次调用都要携带更长的系统提示，成本随技能数量线性叠加。论文没有报"每多一个 token 换多少奖励"，也没有报长技能是否挤掉了任务上下文。

3. **轨迹层检查让奖励可被过程匹配满足**（方法问题）。奖励是"通过检查的比例"，而检查里包含"是否调用了期望的命令"。一个 agent 只要照着技能文档把命令敲一遍，即使状态没改对，也能拿到那部分分。GEPA 看到的梯度里因此混着"把文档写得更像命令清单"这一项，而这与"把事做对"不是一回事。这也解释了为什么优化后的技能主要变长、变成操作清单。

4. **验证器与 agent 在同一个沙箱里，没有讨论奖励劫持**（系统问题）。验证脚本用 SDK 读用户分支的状态，而 agent 有同一个 SDK 的写权限。论文在结论里提到"LLM 容易被奖励劫持，细粒度验证是强化学习的前提"，但没有说明在这套装置里 agent 能不能改到验证器读取的那部分状态（例如往期望的表里手写行来满足断言）。写路径任务的检查若只看"表里有没有这几行"，就是可被直接写出来的。

5. **跨技能的测试泄漏没有被排除**（评估问题）。每个技能从题库里抽"需要该技能"的题，再按 70/15/15 切。但一道多技能任务在技能 A 的划分里可能是训练题，在技能 B 的划分里可能是留出题。论文说多技能任务提升很小，这**间接**说明泄漏没有帮上忙，但没有正面报告重叠比例，也没有做"只用单技能任务"的对照。

6. **平台方自己造基准、自己报结论**（评估问题）。作者来自平台公司，基准建立在平台专有特性上（无头、数据版 Git），结论"这两个特性是可验证性的关键"同时也是产品卖点。开源了实现（`github.com/BauplanLabs/skill-issues`）缓解了这一点，但"换成另一个湖仓还能不能这样验证"没有被测——这恰恰是论文声称最有价值的那部分。

7. **没有便宜的对照**（方法问题）。最自然的对照不是"种子技能"，而是"把官方 SDK 文档整段贴进 `CLAUDE.md`"。如果贴文档就能拿到大部分提升，那么 GEPA 的贡献就只剩"自动挑出该贴哪几段"。这个对照成本很低（一次运行），论文没有做。

8. **数据集人工审查的规模未报**（数据问题）。"领域专家抽样审查任务质量"出现在 §3.2.1，但抽了多少、几个人、分歧怎么处理、有多少条被拒，都没有。相比之下验证器的三层设计写得很细，说明团队知道该记什么，只是没记这一项。

### 创新点

**一、把"技能文档"提升为可优化的系统参数，并给出跨平台的最小可移植条件**

- 主张：任何"agent 通过文本学习如何使用系统"的场景，都可以把这份文本当成参数，用状态验证当奖励来优化；可移植的前提是系统提供"程序化读状态"的能力，不要求是同一个湖仓。
- 与原文关系：增量（原文只做了 Bauplan 一个平台）+ 扩展（把"无头 + 数据版 Git"抽象成两个可检查的条件：状态可程序化读取、操作可原子回滚）。
- 最小验证：在第二个有状态系统（例如带分支的仓库、或带事务的数据库）上照搬同一条流水线，只要求这两个条件成立，看六个技能的提升幅度是否落在 10% 量级。判据是至少三个技能在留出集上显著变好。
- 失败条件：换平台后提升消失或变成负的，说明 28.6% 来自 Bauplan 的特定 API 形状而不是方法本身，可移植性主张不成立。

**二、把优化目标从"奖励"改成"奖励—长度"的 Pareto**

- 主张：技能文档的价值应当按"每多花 1,000 token 换多少通过率"来报。27.2 倍的膨胀很可能远超收益所需的长度，压缩后的技能可能保留大部分提升。
- 与原文关系：反驳（原文的奖励函数不含长度项，导致优化器无节制地加内容）。
- 最小验证：对优化后的六个技能做三档压缩（删掉纯文档指针、删掉重复的最佳实践、只保留与检查项一一对应的句子），在留出集上重测奖励并统计字符数。判据是压缩到 3–5 倍时奖励下降小于 2 个百分点。
- 失败条件：压缩后奖励掉超过 5 个百分点，说明长度与效果强耦合，"细节越多越好"成立，Pareto 主张应降级为"必须报长度"。

**三、把多技能任务当成联合优化问题**

- 主张：真实任务往往是"多技能组合"，逐个技能独立优化会让每个技能都只对自己的检查最优，组合起来反而互相冲突（例如一个技能说"先确认再合并"，另一个说"尽快合并"）。
- 与原文关系：扩展（作者把它列为下一步工作，但没有给出可执行的联合目标）。
- 最小验证：在多技能任务子集上，比较三种配置——各自独立优化的技能、联合优化的一组技能、以及人工合并的版本。指标是端到端通过率与技能间的指令冲突数。判据是联合优化显著高于独立优化。
- 失败条件：联合优化与独立优化差异小于噪声，说明多技能任务的瓶颈在模型能力而不是技能冲突，那么"联合优化"这个方向应当撤销。

**四、把验证器移出 agent 的可写范围**

- 主张：只要 agent 与验证器共享写入权限，奖励就可被直接构造。把断言改成"只能由真实业务操作产生"的形式（例如校验提交的谱系、操作前后的因果链，而不只是终态的行内容），才是强化学习可用的奖励。
- 与原文关系：正交（原文提到奖励劫持是动机，但验证器设计与 agent 同域，没有隔离讨论）。
- 最小验证：构造一个"作弊 agent"，它不执行业务操作、直接往期望的表里写行，看现成的检查能否判它通过。判据是作弊 agent 的通过率应当接近 0。
- 失败条件：作弊 agent 的通过率已经接近 0（说明检查里包含了只有真实操作才能满足的条件，例如提交谱系或副作用顺序），这条主张就是多余的。

**五、把技能优化做成跨模型迁移矩阵**

- 主张：一份技能是否"好"，取决于它服务的模型。同一个技能在强模型上是冗余（模型本来就会），在弱模型上是关键（补上了缺失的程序性知识）。因此技能优化应该产出"按模型档位分层"的版本，而不是一份通用文本。
- 与原文关系：扩展（原文只用 `claude-sonnet-4-6`，作者承认这是初步证据）。
- 最小验证：用同一批种子技能，在两个能力档的模型上各优化一遍，再交叉评测（用 A 模型优化、在 B 模型上评）。判据是交叉组合明显低于同模型组合，且弱模型从优化中获益更多。
- 失败条件：交叉组合与同模型组合差异小于噪声，说明技能内容是模型无关的通用知识，"分层"没有必要。

## 相关工作

与 [RSIHub](wang2026-rsi-hub.md) 的关系最直接：两者都在"改文本/改代码"，但可变面不同。RSIHub 把进化对象放在 harness 代码与配方上，可变面必须显式声明，评测在可变面之外；这篇把可变面收窄到技能文档的文本，评测靠数据状态。前者关心"改动是否可追溯、可复现"，后者关心"改动是否真的让有状态任务做得更好"。两篇都缺同一件事——优化成本账本。

与 [OO-Harness](li2026-oo-harness.md) 的差别在可优化对象的粒度：OO-Harness 改的是类的继承结构（结构性改动），这篇改的是一段说明文字（语义性改动）。有意思的是两者的失败模式互补：结构性改动容易过拟合到某个任务簇，语义性改动容易膨胀到不可维护。

与 [RRSI](xia2026-rrsi.md) 共享"搜索会漂移"的问题，处理方式不同：RRSI 用约束限制候选与编辑空间，这篇用留出集与验证集分离限制选择。两篇都只做了单轮或少量重复，没有报搜索方差。

与 [Agent-Diff](pysklo2026-agent-diff.md) 和 [ThinkingBox](li2026-thinkingbox.md) 是同一族判分思想：都从"看过程"转向"看状态"。差别在闭世界假设。Agent-Diff 用闭世界不变量，没有被断言解释的改动一律判失败；ThinkingBox 用逐条检查连乘，没写的不算；这篇用"期望交互 + 状态断言 + 禁止动作"三段式，介于两者之间。三篇合起来说明一件事：状态判分的严格程度是一个设计变量，不是固定的正确答案。

与 [SAGE](hu2026-sage.md) 都在造基准，但方向相反：SAGE 用固定语料去比较检索器，这篇用生成的任务去优化文本产物。前者关心"评测能不能分辨方法"，后者关心"评测能不能当优化信号"。
