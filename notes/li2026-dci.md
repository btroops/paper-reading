# Beyond Semantic Similarity: Rethinking Retrieval for Agentic Search via Direct Corpus Interaction

## Why

先看一个具体的检索任务。问题是"找一篇 2024 年 NAACL 的论文，它的关键可视化显示某些任务在没有额外代码训练时已经到天花板，并且和 LLM as Tool Makers 共享 14 条引用"。这个问题里没有一个可以直接拿去查的完整句子：它由四条弱线索拼成——年份、会议、图的内容、引用关系。传统检索器接收的是一条查询，返回的是 top-$k$ 文档。它可以把"NAACL 2024"和"tool makers"都算进相似度，但没法表达"先找含 Tool Makers 的文档，再在它引用的论文里筛 NAACL 2024，再在剩下的论文里找带那张图的"。这些约束只能靠 agent 多轮改写查询去逼近，每一轮都要重新经过一次相似度排序。

这就是检索器接口（retriever interface）的限制。不管是 BM25 这样的稀疏检索，还是双塔稠密检索，它们都把语料压缩成一个固定形式的接口：输入查询，输出按相似度排序的 top-$k$ 文档或片段。这个抽象在单轮问答里很高效，因为答案通常集中在一两篇文档里。但 agentic search 的任务形态变了：agent 要发现中间实体、组合弱线索、在读到局部证据后改计划。这些动作需要的是"在文档内部精确匹配一个字符串""把两个关键词的交集找出来""看命中位置前后各三行""在候选文件里再筛一次"。这些操作传统检索器一个都做不了，agent 只能把希望寄托在相似度排序上，希望相关文档排进前 $k$。

更糟的是，被过滤掉的证据无法恢复。检索器返回 top-$k$，第 $k+1$ 篇文档对当前查询可能不相似，但对下一跳是关键的。agent 看不到它，也就不会去查它。后续推理再强，也只能在已经拿到的候选里打转。这不是"检索器不够准"的问题，是"接口只暴露一个排序列表"的问题。换一个更强的 embedding 模型，排序会变好，但接口的形状没变。

成本账也在推着人换接口。稠密检索要离线建索引：切块、编码、写向量库，语料一变就要重建。BrowseComp-Plus 的语料是 10 万篇文档、平均 5,179 词；Wikipedia-18 是 2,101 万篇、平均 100 词。前者建一次索引的成本还可以接受，后者每次语料更新都重建一遍就很贵。而真实 agent 工作区里的语料往往是本地的、异构的、持续变化的：今天新增一份 PDF，明天改一个 Markdown 文件。为这种语料维护向量索引，等于给一个不断变化的目标做快照。

于是问题可以写成四问。第一，如果不给 agent 任何检索器，只给它一个终端和原始语料，让它自己用 `grep`、`find`、`cat` 这些通用工具去找，能不能在端到端任务上超过配好的稀疏、稠密、重排基线？第二，如果能，收益是从哪来的——是找到了更多标准答案文档，还是把已经找到的文档用得更细？第三，这套接口在语料变大时还成立吗，成本怎么涨？第四，如果成立，检索的研究问题是不是应该从"选哪个检索器"改成"设计哪种语料接口"？

## What

先交代任务。输入是一份以文件形式存放的原始语料（BrowseComp-Plus 的网页文本、Wikipedia dump、BRIGHT/BEIR 的文档集合）、一个自然语言问题或查询，以及一个通用终端；输出是答案，或按相关性排序的文档列表。系统不建任何向量索引，不调用任何检索 API，不训练模型；它只让 agent 用 `grep`/`rg` 做精确或正则匹配、用 `find`/`glob` 做文件定位、用 `head`/`tail`/`sed` 或轻量脚本看命中位置前后的局部上下文。边界是：它不改变语料内容，不预计算 embedding，也不依赖网页搜索；语料必须能以文件形式被终端访问。

论文的答案是：这套被作者称为直接语料交互（direct corpus interaction, DCI）的做法，在三个任务族上都超过了配好的检索基线，而且成本更低或相当。在 BrowseComp-Plus 的 830 道题上，同一个 Claude Sonnet 4.6 backbone，把 Qwen3-Embedding-8B 检索器换成 DCI，准确率从 69.0% 升到 80.0%（+11.0 点），成本从 1,440 美元降到 1,016 美元（-29.4%）；它也比最强的检索基线（GPT-5 + Qwen3-Embedding-8B，71.7%）高 8.3 点（Fig. 1, §4.2）。在多跳问答的六个数据集上，DCI-Agent-CC 平均 83.0%，比最强的检索 agent 基线 ASearcher-Local-14B（52.3%）高 30.7 点；轻量版 DCI-Agent-Lite 平均 68.0%，高 15.7 点（Table 2）。在 IR 排序的六个数据集上，DCI-Agent-CC 平均 NDCG@10 68.5，比最强的重排基线 ReasonRank-32B（47.0）高 21.5 点；轻量版 56.7，高 9.7 点（Table 3）。`[已验证，Table 2, Table 3, Fig. 1]`

### 新认识：瓶颈不是召回，是"找到之后能不能在文档内部继续操作"

第一个认识是，DCI 的优势主要不来自"找到更多标准答案文档"。作者在 BrowseComp-Plus 上做了逐题配对：DCI-Agent-CC 答对而检索 agent 答错的题有 176 道，反向只有 76 道。在这 176 道里，只有 34 道是检索 agent 完全没找到任何标准答案文档；其余 142 道里，检索 agent 已经找到了至少一篇标准答案文档，但仍然答错（§4.3）。这 142 道又分两类：83 道是"部分链"（找到了部分证据，但没桥接到下一跳），59 道是"检索后失败"（标准答案文档全找到了，但没用起来）。也就是说，大部分差距发生在"文档已经进入上下文之后"，不是"文档没被召回"。`[已验证，§4.3, Fig. 4 左]`

第二个认识是，DCI 用覆盖率换定位精度。作者定义了两个轨迹级指标：覆盖率（coverage）看轨迹有没有碰到标准答案文档，定位度（localization）看碰到之后能不能收窄到一小段可用证据。在 100 题子集上，DCI-Agent-Lite 的平均覆盖率只有 28.0%，远低于 Qwen3-Embedding-8B 的 56.7%；但"至少碰到一篇"的覆盖率是 70.0%，与检索的 74.0% 接近；定位度是 48.4，比检索的 21.7 高一倍多；准确率 73.0%，比检索的 45.0% 高 28 点（Table 4）。BrowseComp-Plus 的题通常只有 1–4 篇标准答案文档，所以"至少碰到一篇"比"把整条链都召回"更划算：碰到一篇之后，DCI 可以停下来在文档内部精确搜索、验证、抽取，而不是继续在语料层面广撒网。`[已验证，Table 4；100 题子集，单次运行]`

第三个认识是，工具的表达力有边际收益，但不是全部。作者做了工具集消融：只给 `read + grep`（不能跑任意 shell），DCI-Agent-Lite 在 100 题子集上 61%，已经比 Qwen3-Embedding-8B 的 45% 高 16 点，工具调用次数几乎相同（19 对 18）；放开完整 bash 后升到 73%，但工具调用涨到 35 次、每题成本从 0.0355 美元涨到 0.1021 美元（Table 5）。这说明"高分辨率接口"的核心是精确匹配加局部阅读，不是"能跑任意脚本"；后者带来 12 点增益，代价是约三倍成本。`[已验证，Table 5]`

### 新方法：两种脚手架、一套上下文管理、两个轨迹指标

第一件可复用的东西是接口本身。DCI 把"检索"从"调用一个排序函数"改成"在文件系统上执行命令"。命令可以管道组合：`grep 'foo' file | grep 'bar'` 表达两个词的合取；`find . | grep 'report' | grep '2024'` 表达路径与年份的合取；`grep -n 'keyword' file | head` 表达"只看命中位置附近"。这些组合是传统 top-$k$ 接口无法直接表达的。作者把这种能力叫"检索接口分辨率"（retrieval interface resolution）：分辨率指能在比整篇文档或段落更小的单位上操作的能力。

第二件是两个脚手架。DCI-Agent-Lite 基于 Pi（一个极简终端编码 agent），只暴露 `bash` 与 `read`，用来做受控实验：没有检索模块、没有索引、没有重排器，收益只能来自接口。DCI-Agent-CC 基于 Claude Code，用它的提示、工具编排和内置上下文处理，用来探性能上限；两者都只通过终端访问语料，不调用 embedding 检索器。这个双脚手架设计是为了把"接口"与"harness 工程"分开：Lite 证明接口本身有效，CC 证明同一接口在更强 harness 下还能涨。

第三件是运行时上下文管理。DCI 的观察是工具输出：`grep` 可能返回几百行，`cat` 可能返回整篇文档。长轨迹里这些输出会撑爆上下文。作者用三种机制：截断（truncation，每次工具结果最多保留 20K 或 50K 字符）、压缩（compaction，累计工具输出超过 240K 字符时，把较早的工具结果清空成占位符，保留最近 12 轮）、摘要（summarization，压缩后仍然超限时，让模型生成摘要，保留最近 20K token）。三种机制组合成 L0–L4 五档策略，用来做消融。

第四件是评估装置。覆盖率有三个聚合：至少一篇（any）、平均召回（mean）、全部（all）。定位度把每次观察里的片段长度与标准答案文档长度比较，片段越短、越集中，分数越高；公式用对数比值，见 How 三。两个指标合起来，才能区分"找到了但没读透"和"没找到"。

### 新结论：成立条件、成本曲线与失效边界

成立条件有三条。第一，语料必须能以文件形式被终端访问；如果语料在远端数据库或只能通过 API 访问，DCI 不适用。第二，模型必须足够强，能自己规划搜索、组合命令、判断何时停；论文的两个脚手架分别用 GPT-5.4 nano 与 Claude Sonnet 4.6，都是前沿模型。第三，语料规模不能太大：作者把 BrowseComp-Plus 从 10 万篇扩到 20 万篇，工具调用从 38.5 涨到 86.9，延迟翻倍多，成本翻倍多，准确率掉 13.6 点；扩到 40 万篇时准确率掉到 37.5%，平均 122.4 次工具调用，20 道题撞上最大工具预算（Fig. 5, §4.3）。`[已验证，Fig. 5]`

成本曲线不是单调的。在 BrowseComp-Plus 全量上，DCI-Agent-CC 比同 backbone 的检索 agent 便宜 29.4%（1,016 对 1,440 美元），原因是检索 agent 每步把 top-$k$ 文档塞进上下文，而 DCI 只返回命中行；但 DCI-Agent-Lite 在 100 题子集上每题 0.1021 美元，比 Qwen3-Embedding-8B 的 0.0498 美元贵一倍，因为它平均调用 35 次工具，检索只调用 18 次（Table 4）。所以"更便宜"取决于比较对象与脚手架：强 harness 下省的是上下文 token，弱 harness 下多花的工具调用可能抵掉节省。`[已验证，Fig. 1, Table 4；成本只算 agent 侧]`

失效边界有三类。第一类是语料规模：超过 20 万篇后，定位第一篇有用文档的成本急剧上升。第二类是任务类型：DCI 在需要广覆盖的任务上不占优，平均覆盖率只有 28.0%，如果任务要求找齐所有相关文档（例如系统性综述、召回率优先的检索），DCI 会漏。第三类是上下文管理：五档策略的准确率是非单调的，L3 最好（77），L2 最差（69），L4 反而回落到 73；L3 的延迟是 8,712 秒/100 题，L0 是 2,226 秒，差了近四倍（Table 6）。这说明 DCI 的收益依赖运行时策略，策略选错会吃掉接口优势。`[已验证，Table 6；100 题子集]`

## How

这篇论文跨两类。系统与算法类：它定义了一种检索接口、两个 agent 脚手架、一套上下文管理策略和两个轨迹指标。实证与基准类：它在三个任务族、十四组基线上做端到端比较，另有工具集消融、语料扩展、上下文管理消融和逐题配对分析。判型依据是它既给出可复用的接口设计，又用统一评测验证；没有定理，没有新的训练目标，也不训练模型。下面按"接口—脚手架—指标—实验—机制—成本—边界"展开。

### 一、接口：把排序函数换成命令组合

传统检索接口的形式是 $R(q)\to\{(d_1,s_1),\dots,(d_k,s_k)\}$：输入查询 $q$，输出 $k$ 篇文档及相似度分数。DCI 的接口是 $T(c)\to o$：输入一条命令 $c$，输出一段工具观察 $o$，$o$ 可以是匹配行、文件路径、计数、局部上下文。两者最根本的差别是：传统接口的候选集在调用返回时就固定了，DCI 的候选集可以在下一次调用里继续缩小。

用论文里的一个实际轨迹走一遍。问题是"一本书，2013 到 2016 年间 5 月出版，主角发现一个装满某种海洋生物的坦克，遇到一个男孩并给他起了一个基于眼睛颜色的绰号，校长痴迷于记分牌，作者从小写作画画，2023 年 12 月前空闲时间打电子游戏"。DCI-Agent-Lite 的第一条命令是 `find bc_plus_docs -maxdepth 2 -type f | head`，先看目录结构；然后用 `rg` 搜"tank""scoreboard"等词，逐步缩小到候选文件；最后 `read` 候选文件确认。这个过程中，每一步的候选集都是上一步的输出，而不是一个固定的 top-$k$。`[§D.3]`

命令的组合性是关键。`grep 'foo' file | grep 'bar'` 把两个词的交集作为候选；`rg -n 'keyword1' | rg 'keyword2'` 先在语料层筛，再在结果里筛；`cat file | head -50` 只看文件开头。这些管道在 shell 里是普通操作，但对检索接口来说，它们把"约束"变成了可执行的过滤器，而不是相似度分数里的一个维度。

### 二、脚手架：Lite 与 CC 各回答一个问题

DCI-Agent-Lite 的目标是"最小接口"。它基于 Pi，只给 `bash` 与 `read`，没有任何检索专用模块：没有离线索引、没有稠密检索器、没有重排器。模型是 GPT-5.4 nano，推理强度 high，最大 300 轮。这个配置故意弱，用来回答"只换接口、不换 harness，收益还在不在"。

DCI-Agent-CC 的目标是"性能上限"。它基于 Claude Code，保留其默认提示与工具编排，但禁用网页搜索、网页抓取和子 agent，并阻断数据目录以防答案泄漏。模型是 Claude Sonnet 4.6，推理强度 medium，最大 300 轮。这个配置回答"同一个接口在成熟 harness 下能走多远"。

两者的对照很重要，因为 DCI 的收益可能来自三个地方：接口本身、harness 的工程、模型的强弱。Lite 把后两个压到最低，CC 把后两个拉满；如果两者都超过检索基线，接口的贡献就更可信。但这也带来归因问题：CC 与检索基线的 harness 不同，见 Ideas。

### 三、轨迹指标：覆盖率与定位度

覆盖率回答"有没有碰到标准答案文档"。设 $D^*(q)$ 是问题 $q$ 的标准答案文档集合，$M(q,\tau)$ 是轨迹 $\tau$ 里显式出现过的标准答案文档集合（检索片段或工具返回的文件都算），则

$$
\operatorname{coverage}_{\text{any}}(q,\tau)=\mathbb{1}[|M(q,\tau)|\ge 1],\qquad
\operatorname{coverage}_{\text{mean}}(q,\tau)=\frac{|M(q,\tau)|}{|D^*(q)|},\qquad
\operatorname{coverage}_{\text{all}}(q,\tau)=\mathbb{1}[|M(q,\tau)|=|D^*(q)|].
$$

三个聚合分别看"至少一篇""平均召回""全部找到"。它们都是语料层面的指标，不关心文档内部读了多少。

定位度回答"碰到之后有没有收窄到一小段"。设一次观察 $o_t$ 暴露了若干候选 $(d_{t,i},\sigma_{t,i})$，其中 $\sigma_{t,i}$ 是片段，$\ell_{t,i}=|\sigma_{t,i}|$ 是片段字符长度。把长度换成固定宽度的段数：$\nu(x)=\max(1,\lceil x/c_{\text{seg}}\rceil)$；再用对数比值给分：

$$
\psi(a;b)=\max\left(1-\frac{\log a}{\log b},\,0\right),\qquad 1\le a\le b,\ b>1,
$$

其中 $a$ 是片段段数，$b$ 是标准答案文档段数。片段越短，$a$ 越小，$\psi$ 越接近 1；片段等于整篇文档时 $\psi=0$。对每个标准答案文档 $d^*$，取轨迹里所有对齐候选的最高分：

$$
s(d^*,\tau)=\max_{d_{t,i}\in H(d^*,\tau)}\operatorname{seg\text{-}score}(d_{t,i};d^*),
$$

再对所有碰到的标准答案文档取平均，得到 $\operatorname{localization}(q,\tau)$。这个指标的设计意图是：DCI 的 `grep` 只返回命中行，片段很短，定位度天然高；检索器返回的 preview 较长，定位度天然低。所以它是"接口分辨率"的操作化定义，不是中立的准确率指标，见 Ideas。

### 四、实验设置：三个任务族，两套模型，十四组基线

Agentic search 用 BrowseComp-Plus：10 万篇文档、平均 5,179 词，830 道题，官方语料与 FAISS 索引都放出；检索基线用 BM25 与 Qwen3-Embedding-8B，backbone 包括 GPT-5、o3、GLM-4.7、Claude Sonnet 4.5/4.6。知识密集型 QA 用 NQ、TriviaQA、Bamboogle、HotpotQA、2WikiMultiHopQA、MuSiQue，语料是 2018 年 Wikipedia dump（2,101 万篇，平均 100 词）；检索基线用 E5 建索引。IR 排序用 BRIGHT 的 Biology、Earth Science、Economics、Robotics 四个域，以及 BEIR 的 ArguAna、SciFact；指标是 NDCG@10。除 BRIGHT 与 Bamboogle 跑全量外，其他数据集随机采样 50 题；ArguAna 从 1,406 题采 50，SciFact 从 300 题采 50（§A.1）。判定器是 GPT-4.1，只比较预测答案与参考答案（§A.3）。

这个设置里有三个口径要记住。第一，QA 与 IR 的 50 题采样很小，主表的平均值没有置信区间。第二，DCI-Agent-CC 与检索基线的 backbone 不完全相同：CC 用 Sonnet 4.6，检索基线里有 Sonnet 4.6，也有 GPT-5、o3、GLM-4.7；多跳 QA 的最强基线 ASearcher-Local-14B 是 14B 开源模型。第三，成本只算 agent 侧调用，不含索引构建、judge 调用和语料准备。

### 五、结果：三个任务族、两组脚手架

BrowseComp-Plus 的结果前面给过：CC 80.0 对同 backbone 检索 69.0，成本 1,016 对 1,440 美元；Lite 62.9，成本 93 美元，接近 o3 的 66.0（成本 740 美元）。Fig. 1 把准确率与成本画成帕累托前沿：DCI 的两个点在检索 agent 的左上方，意思是同等成本更准、同等准确更便宜。`[已验证，Fig. 1]`

多跳 QA 的数字要按数据集看，因为平均值会掩盖结构。CC 在 NQ 78、TriviaQA 96、Bamboogle 80、HotpotQA 88、2Wiki 82、MuSiQue 74；Lite 是 72、84、72、72、68、40。最强检索 agent 基线 ASearcher 是 56、58、62、58、56、24（Table 2）。CC 的优势在 MuSiQue 最大（+50），在 NQ 最小（+22）；Lite 在 MuSiQue 只有 40，说明最难的多跳链对弱模型仍然吃力。`[已验证，Table 2]`

IR 排序的分布也值得看。CC 在六个数据集上是 77.1、69.0、46.8、56.8、85.3、75.7，平均 68.5；Lite 是 60.0、50.8、32.3、42.4、81.9、72.7，平均 56.7；ReasonRank 是 58.2、48.9、36.6、33.9、28.7、75.5，平均 47.0（Table 3）。CC 在 ArguAna 上 85.3 对 ReasonRank 28.7，差距最大；在 SciFact 上 75.7 对 75.5，几乎持平。这说明 DCI 的优势集中在需要组合多条弱线索的检索任务上，在单条 claim 的事实核验上不一定更好。`[已验证，Table 3]`

### 六、机制：逐题配对、工具分布与覆盖率-定位度权衡

逐题配对是本文最有力的机制证据。BrowseComp-Plus 830 题里，CC 赢 176 题、输 76 题，净胜 100 题；176 个胜场里只有 34 个是检索完全没找到标准答案文档，142 个是"检索找到了但没用起来"。142 个里 83 个是部分链（找到了部分证据，没桥接到下一跳），59 个是检索后失败（标准答案文档全找到，但推理或使用失败）。这把"接口优势"从抽象说法落到了具体失败位置：不是召回不够，是召回之后的操作不够细。`[已验证，Fig. 4 左, §4.3]`

工具分布支持同一解释。CC 的调用里 Bash 占 62.4%、Grep 占 33.0%；Bash 内部，链式搜索（`rg | rg`）占 22.3%、局部上下文查看占 18.0%、正则匹配占 17.0%、文件定位占 14.0%、整篇阅读只占 9.1%（Fig. 4 右）。Lite 的 3,168 条命令里，`rg | head` 占 56.2%、`rg | rg` 占 20.6%、`wc` 占 7.8%、单关键词 `rg` 占 6.3%、`ls` 占 4.3%、`python -c` 占 2.4%、`find` 占 2.1%、`cat` 只占 0.1%（Fig. 6, §B.1）。两组轨迹都显示：agent 主要在做"搜索加限制""链式过滤""局部查看"，几乎不整篇读。这正是"高分辨率接口"的行为签名。`[已验证，Fig. 4, Fig. 6]`

覆盖率与定位度的权衡是机制的另一面。DCI-Lite 的平均覆盖率 28.0 对检索 56.7，但定位度 48.4 对 21.7，准确率 73.0 对 45.0（Table 4）。这三个数放在一起说明：DCI 没有把整条证据链找齐，但它找到一篇之后就停下来精查；检索器把更多标准答案文档放进候选，但每篇只给一个 preview，agent 没有在文档内部继续操作的手段。对于只有 1–4 篇标准答案文档的 BrowseComp-Plus，前一种策略更划算。`[已验证，Table 4]`

### 七、成本：省在上下文，花在工具调用

成本结构可以从两个对照看。BrowseComp-Plus 全量上，CC 比同 backbone 检索便宜 29.4%（1,016 对 1,440 美元），尽管 CC 的工具调用更多；原因是检索 agent 每次把 top-$k$ 文档的内容放进上下文，而 DCI 的 `grep` 只返回命中行，单次观察短得多。100 题子集上，Lite 每题 0.1021 美元，检索 0.0498 美元，贵一倍；原因是 Lite 平均 35.35 次工具调用，检索 17.55 次，每次调用都要一次模型生成。`[已验证，Fig. 1, Table 4]`

这两个数不矛盾，它们说明成本由两部分组成：上下文 token 与工具调用次数。DCI 把前者压小、把后者抬高；哪一部分占主导，取决于 harness 是否支持并行调用、模型是否擅长少步数完成、检索器返回的文档有多长。论文没有拆这两部分的金额，也没有报延迟的分位数；Table 4 只有单题平均成本，Table 6 有 100 题总延迟，没有 p50/p99。`[系统问题]`

### 八、上下文管理与扩展：甜点区很窄

五档上下文策略的结果是非单调的。L0（不管）准确率 72、延迟 2,226 秒、每题 0.0716 美元；L1（只截断到 50K 字符）75、1,820 秒、0.0720 美元；L2（截断到 20K）69、4,413 秒、0.0590 美元；L3（20K + 压缩）77、8,712 秒、0.1109 美元；L4（再加摘要）73、4,531 秒、0.1021 美元（Table 6）。L3 最准，但延迟是 L0 的近四倍、成本高 55%；L2 最便宜，但准确率比 L0 还低 3 点。作者的解释是：压缩太弱会让 agent 在长历史里漂移，压缩太猛会丢掉中间约束；L3 的"保留最近 12 轮、清空更早的工具结果"刚好落在甜点区。`[已验证，Table 6；100 题子集，单次运行]`

语料扩展的结果更直接地划出边界。10 万篇时 CC 平均 38.5 次工具调用；20 万篇时 86.9 次，延迟翻倍多，成本翻倍多，准确率掉 13.6 点；40 万篇时 122.4 次，准确率 37.5%，20 道题撞上 300 轮上限（Fig. 5, §4.3）。原因是 DCI 没有索引，定位第一篇有用文档要靠 `grep` 扫目录；候选空间翻倍，扫描成本也翻倍。作者的结论是"DCI 在搜索深度上扩展好，在搜索广度上成本涨得快"。`[已验证，Fig. 5]`

## Ideas

### 不足

**评估与统计**

1. 除 BRIGHT 与 Bamboogle 外，所有数据集只随机采样 50 题；BrowseComp-Plus 子集是 100 题。样本小，主表平均值没有置信区间，也没有重复运行。L3 比 L0 高 5 点、L4 比 L3 低 4 点这类差距，很可能落在采样噪声里。`[评估问题]`
2. 判定器是 GPT-4.1，只比较最终答案与参考答案；它不看推理过程，也不看证据路径。DCI 的答案可能靠"猜中"或"搜到答案字符串"而不是靠证据链，判定器无法区分。`[评估问题]`
3. 成本只算 agent 侧调用，不含检索基线的索引构建、DCI 的语料准备、judge 调用。BrowseComp-Plus 的 FAISS 索引是官方放出的，但建索引的成本没有计入；Wikipedia-18 的 2,101 万篇文档如果每次重建索引，成本会很高。`[评估问题]`

**归因与方法**

4. DCI-Agent-CC 用 Claude Code，检索基线用官方 agentic pipeline；两者虽然同 backbone（Sonnet 4.6），但 harness 的提示、工具编排、上下文管理不同。CC 的优势里有多少来自 Claude Code 的工程，多少来自 DCI 接口，没有拆开。`[方法问题]`
5. 多跳 QA 的最强基线 ASearcher-Local-14B 是 14B 开源模型，DCI-CC 是 Sonnet 4.6；模型代差很大，+30.7 点不能归因于接口。DCI-Lite 用 GPT-5.4 nano，与 ASearcher 也不同模型。缺少"同模型、同 harness、只换接口"的对照。`[方法问题]`
6. IR 排序的比较不是同预算：DCI 可以遍历语料、逐篇读，ReasonRank 只对 BM25 提供的候选做重排；DCI 的输出上限是 20 篇，但搜索过程不受 top-$k$ 限制。差距里有一部分是"搜索预算"而不是"接口分辨率"。`[方法问题]`
7. 定位度指标对 DCI 有利：`grep` 返回一行，片段天然短；检索器返回 preview，片段天然长。作者在 §A.3 给 DCI 的片段映射做了保守规定（路径级暴露按整篇文档算），但指标的构造仍然偏向细粒度接口。`[方法问题]`
8. 逐题配对的 176 个胜场里，142 个是"检索已找到标准答案文档但答错"；这只说明检索 agent 的后处理弱，不直接说明 DCI 接口更好。一个"检索 + 局部 grep"的混合系统可能同时拿到两边的好处，论文没有测。`[方法问题]`

**系统与边界**

9. 语料扩展到 20 万篇就掉 13.6 点，40 万篇掉到 37.5%；DCI 的 `grep` 扫目录是线性成本，缺少索引层。论文承认这是 operating envelope，但没有给出"多大语料该换回检索"的判据。`[系统问题]`
10. 上下文管理五档的延迟从 2,226 秒到 8,712 秒（100 题），差近四倍；论文没有报 p50/p99 延迟，也没有报并行工具调用对延迟的影响。`[系统问题]`
11. 防泄漏只写了 CC 阻断数据目录；Lite 是否阻断、如何阻断没有写。BrowseComp-Plus 的语料是网页文本，答案字符串可能直接出现在某个文件里，agent 可以 `grep` 答案而不是找证据。论文没有做"答案泄漏检测"。`[系统问题]`
12. 没有与 A-RAG 这类"agent + 检索工具"的最强形态对比。A-RAG 证明 agent 自主多轮调用向量检索也能很强；DCI 只与传统检索器比，"接口"与"自主性"仍然混在一起。`[方法问题]`

**内部矛盾**

13. §4.1 写主结果用 L3、消融用 L4；但 Table 4 的 DCI-Agent-Lite 标的是 L4，Table 6 又是 L0–L4 全扫。主结果图 1 的 Lite 用哪一档没有标，读者无法确认 62.9% 与 73.0% 是否同一配置。`[评估问题]`
14. 正文说 DCI-Agent-CC "exceeds the strongest retrieval baseline overall, GPT-5 + Qwen3-Embedding-8B (71.7%), by +8.3 points"；但同一段的同 backbone 对照是 69.0%。两个基线不同（GPT-5 vs Sonnet 4.6），+8.3 与 +11.0 不能混用。`[评估问题]`

### 创新点

**一、同预算对照：只换接口，不换模型、不换 harness**

- **主张**：把 DCI 与检索 agent 放在同一个模型、同一个 harness、同一 token/美元预算下比较，DCI 的准确率优势会缩小，但定位度优势仍在；缩小后的差值才是接口的真实贡献。
- **与原文关系**：反驳/修正。原文的 CC 对检索基线换了 harness，Lite 对 ASearcher 换了模型。
- **最小验证**：用同一个 Claude Code harness，把工具集换成"Qwen3-Embedding-8B 检索器 + 文档阅读"与"bash + grep + read"两组，模型、提示、轮数预算、美元预算都相同；在 BrowseComp-Plus 100 题上比较准确率、定位度、工具调用次数。预期 DCI 仍高 5–10 点，但低于原文的 +11。
- **失败条件**：同预算下 DCI 不高于检索基线，或差距小于 3 点。这说明原文的优势主要来自 harness 或模型，不是接口。

**二、混合接口：先向量粗排，再 grep 精查**

- **主张**：把检索器当作"定位第一篇候选文档"的粗排层，把 DCI 当作"文档内部精查"的细排层，能在 20 万篇以上语料上同时保住 DCI 的定位精度与检索的广度。
- **与原文关系**：扩展。原文的 DCI 在 20 万篇掉 13.6 点，瓶颈在"找第一篇"；检索器正好补这一段。
- **最小验证**：在 20 万与 40 万篇 BrowseComp-Plus 上，比较三种接口：纯 DCI、纯 Qwen3 检索、检索 top-20 后用 DCI 在候选文档内 grep/read。指标是准确率、每题工具调用、美元成本。预期混合接口在 40 万篇上把准确率从 37.5% 拉回 55% 以上，成本低于纯 DCI。
- **失败条件**：混合接口不优于纯 DCI，或成本高于纯检索。这说明粗排阶段引入的候选集限制了后续精查，或者 DCI 的收益只在"从零开始找"时成立。

**三、给 grep 建轻量索引：trigram 或倒排，不改变接口语义**

- **主张**：在不改变"精确匹配 + 局部阅读"接口的前提下，给语料建 trigram 索引或倒排索引，把 `grep` 的全语料扫描降到亚线性，能让 DCI 在 100 万篇级语料上保持可用。
- **与原文关系**：增量。原文把"无索引"当作优点（零离线成本、适应变化），但代价是扫描成本线性涨。
- **最小验证**：在 Wikipedia-18 的 2,101 万篇上，比较原始 `rg` 与 trigram 索引的查询延迟（p50/p99）、索引构建时间、索引占用；在同一批 QA 题上比较准确率与工具调用。预期延迟降一个数量级，准确率不变。
- **失败条件**：索引构建成本超过检索器，或索引让语料更新变复杂、失去"适应变化"的优势。这时"无索引"仍是更好的默认。

**四、把定位度做成过程奖励，训练小模型学会"先粗后细"**

- **主张**：DCI 的成功轨迹里有稳定的行为模式（先 `ls` 看目录、再 `rg` 粗筛、再 `rg | rg` 收窄、最后 `read` 确认）；用这些轨迹做过程监督，能让 7B 级模型在少步数下达到接近前沿模型的准确率。
- **与原文关系**：正交。原文不训练，只评测现成模型。
- **最小验证**：用 CC 在 BrowseComp-Plus 上收集成功轨迹，按"覆盖率增益 / 定位度增益 / 步数"打过程分；蒸馏一个 7B 模型预测下一条命令；在 100 题上比较准确率、工具调用、成本。预期工具调用降 40%，准确率掉不超过 3 点。
- **失败条件**：蒸馏后准确率掉超过 8 点，或工具调用不降。这说明 DCI 的决策依赖前沿模型的隐式判断，难以用行为克隆复现。

**五、答案泄漏检测：区分"找到证据"与"搜到答案"**

- **主张**：在 DCI 的评测里加入答案泄漏检测（例如检查 agent 是否直接 `grep` 参考答案字符串、是否读到标注文件），能把"真检索"与"抄答案"分开；这会影响所有 DCI 类系统的可信度。
- **与原文关系**：正交，针对评估漏洞。
- **最小验证**：对 BrowseComp-Plus 的 100 条轨迹做审计：统计 `grep` 模式与参考答案的字符串相似度、检查是否访问标注目录；把可疑轨迹剔除后重算准确率。预期剔除比例低于 5%，准确率下降不超过 2 点。
- **失败条件**：剔除比例超过 15%，或准确率下降超过 5 点。这说明 DCI 的分数有相当一部分来自泄漏，原文结论需要重估。

**六、跨论文：把 A-RAG 的三层工具接进 DCI**

- **主张**：A-RAG 的 `keyword_search`/`semantic_search`/`chunk_read` 可以作为 DCI 的"结构化工具"与 bash 并存；在语料有稳定分块时，用结构化工具减少 `grep` 的盲目扫描，在语料异构时退回 bash。这个混合接口能覆盖两边各自的失效场景。
- **与原文关系**：正交，组合两篇论文的机制。
- **最小验证**：在 BrowseComp-Plus 与 MuSiQue 上比较三种配置：纯 DCI、纯 A-RAG、DCI + A-RAG 工具；指标是准确率、检索 token、工具调用、成本。预期混合在 BrowseComp-Plus 上接近 DCI，在 MuSiQue 上接近 A-RAG。
- **失败条件**：混合配置被任一单配置支配，或工具选择本身消耗过多步数。这说明两种接口的切换成本高于收益。

## 相关工作

仓库内与本文最接近的是 [du2026-a-rag](du2026-a-rag.md)：两者都反对"固定 top-$k$ 检索"，都把检索决定权交给 agent。区别在接口的激进程度：A-RAG 仍然保留向量索引，只是把索引暴露成三个粒度可选的工具；DCI 把索引整个去掉，让 agent 直接在文件系统上操作。A-RAG 的 `keyword_search` 是语料级字面匹配，DCI 的 `grep` 是文件级正则匹配，后者更细，但需要 agent 自己处理目录结构与文件格式。

[wan2026-decision-rag](wan2026-decision-rag.md) 也把层级检索的展开决定交给一个判断器，但它的判断器是专门的决策模型，不是通用终端；DCI 把"判断"与"执行"都交给同一个 LLM，用命令组合表达约束。

[kumar2026-stair](kumar2026-stair.md) 用目录叶节点当检索单位，DCI 用文件路径与命中行当检索单位；前者依赖结构化目录，后者不依赖任何结构，适应性更强，但缺少"全局导航"的抓手。

[bao2026-raw-rag](bao2026-raw-rag.md) 的结论是"配好的原始历史检索比复杂记忆系统更强"；DCI 把这条线推到极端：连检索器都不要，直接用原始语料。两篇都在问同一个问题——复杂中间层到底买到了什么。

[he2026-memory-tax](he2026-memory-tax.md) 的收益/税账本可以补本文缺的成本分解：DCI 省了上下文 token，花了工具调用，净账要看两者价格。

[ho2026-declarative-attention](ho2026-declarative-attention.md) 让模型自己声明读哪些 KV 块，DCI 让模型自己声明查哪些文件与行；两者都是"把接口的控制权交给模型"，粒度不同。

## 可复现

- 代码：<https://github.com/DCI-Agent/DCI-Agent-Lite>（首页给出）。
- 数据：BrowseComp-Plus 官方语料与 FAISS 索引；Wikipedia-18 dump（2,101 万篇）；BRIGHT 四个域；BEIR 的 ArguAna 与 SciFact。DCI 需要把语料落成文件目录，目录结构会影响 `find`/`grep` 的效率，论文没有给目录组织规范。
- 模型：DCI-Agent-Lite 用 GPT-5.4 nano（reasoning high）；DCI-Agent-CC 用 Claude Sonnet 4.6（reasoning medium）；judge 用 GPT-4.1。
- 关键超参：最大 300 轮；上下文管理 L3（主结果）/L4（消融）；截断 20K 或 50K 字符；压缩阈值 240K 字符、保留最近 12 轮；摘要保留最近 20K token、连续 3 次失败后停止；IR 输出上限 20 篇文档。
- 无法复现的部分：随机采样 50 题的种子、每次运行的美元成本明细、p50/p99 延迟、Lite 的答案泄漏防护、DCI 片段映射的完整实现、CC 的完整系统提示。论文只给了 QA/IR 提示模板（§C.1, §C.2），没给 CC 的 harness 配置。
