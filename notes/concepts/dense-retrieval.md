# 稠密检索：文本怎么变成向量，什么被保留、什么被丢掉

这篇解释 [SAGE](../hu2026-sage.md) 的 Why 里被压缩的一句话："用大模型做稠密编码，用指令微调让检索器理解任务描述，用推理链扩展查询。"这三个说法分别指什么、为什么合起来叫"让检索器也会推理"、以及为什么这套东西到了 agent 场景可能失效。

## 一、检索在做什么

检索系统做一件事：给一个查询，把语料里的文档按相关性排序，返回前 $k$ 篇。所有检索方法最后都要落到一个分数 $s(q,d)$，分数高的排前面。分歧在于这个分数怎么算。

有两种算法。第一种数词：查询里的词在文档里出现了几次、这个词在全库有多稀有。第二种算向量：把查询和文档各压成一串数字，看两串数字有多接近。前者叫稀疏检索，后者叫稠密检索。

## 二、BM25：每个词单独计分

BM25 是稀疏检索的代表。它先把每篇文档切成词，离线建一张倒排表：每个词记录自己出现在哪些文档、出现几次、在每篇文档的什么位置。查询进来时，查询里的每个词去表里查，按下面的公式打分：

$$
\operatorname{score}(q,d)=\sum_{t\in q}\operatorname{IDF}(t)\cdot
\frac{f(t,d)\cdot(k_1+1)}{f(t,d)+k_1\cdot\left(1-b+b\cdot\frac{|d|}{\operatorname{avgdl}}\right)}.
$$

逐个符号解释。$t$ 是查询里的一个词；$f(t,d)$ 是词 $t$ 在文档 $d$ 里出现的次数；$|d|$ 是文档长度；$\operatorname{avgdl}$ 是语料的平均文档长度；$k_1$ 控制词频的饱和速度，$b$ 控制长度归一化的强度，常用取值是 $k_1=1.2$、$b=0.75$。$\operatorname{IDF}(t)$ 是逆文档频率：一个词在越少的文档里出现，它的区分度越高，权重越大。所以稀有词（模型名、会议名、年份）的分数高，常见词（the、of）的分数低。

这个公式的直觉是：一个词在文档里出现得越多，文档越可能相关，但收益会饱和，出现 10 次不比出现 5 次强一倍；文档越长，越容易碰巧包含某个词，所以要按长度打折。

BM25 的特点是每个词独立计分，最后相加。它只认字面：查 `ODEFormer` 不会命中 `Ordinary Differential Equation Transformer`；查"心梗"不会命中"心肌梗死"，除非额外加同义词表。反过来，它不会丢掉任何词面约束：查询里的年份、会议名、数字，只要在文档里出现，就会贡献分数。

## 三、稠密检索：整段文本一个向量

稠密检索把打分换成向量相似度。它先训练一个编码器 $f$，把任意一段文本压成一个固定长度的向量：

$$
v_q=f(q),\qquad v_d=f(d),\qquad s(q,d)=\frac{v_q^{\top}v_d}{\lVert v_q\rVert\,\lVert v_d\rVert}.
$$

$v_q$ 和 $v_d$ 是查询和文档的向量，维度通常是几百到几千，比如 768、1,024、3,584。$s(q,d)$ 是余弦相似度，取值在 -1 到 1 之间：方向越接近，分数越高。

向量的每一维没有可读含义。你没法指着第 37 维说"这一维代表会议名"；它是训练出来的稠密表示，信息分散在所有维度上。这一点是理解后面所有问题的关键：词面匹配保留的是"哪个词出现了"，稠密向量保留的是"整体意思像不像"，前者是离散的、可解释的，后者是连续的、压缩的。

### 3.1 编码器在做什么

编码器是一个神经网络。输入一段文本，先切成 token（子词），每个 token 查一张词表变成一个初始向量；然后过若干层 Transformer，每层让每个 token 的向量吸收上下文信息；最后每个 token 得到一个向量。

注意：一个句子有 $n$ 个 token，就得到 $n$ 个向量，不是"一个句子一个向量"。要做检索，必须把 $n$ 个向量压成一个句向量，这一步叫池化（pooling）。常见做法有两种：

- **平均池化**（mean pooling）：把 $n$ 个向量逐维平均，得到 1 个向量。
- **取最后一个 token**（last-token pooling）：直接取最后一个 token 的向量。decoder-only 模型是因果注意力，最后一个 token 能看到前面所有 token，所以它的向量可以代表整句。

第一代稠密检索器（如 DPR）用 BERT 做编码器。BERT 是双向的，每个 token 能看到左右两边，通常取开头的 `[CLS]` token 做句向量。查询和文档各用一个编码器（双塔），文档可以离线编码好存进向量库，查询只在检索时算一次。

### 3.2 向量相似度怎么变成排序

建索引时，把语料里每篇文档编码成一个向量，存进向量库（FAISS、HNSW 之类）。检索时，把查询编码成一个向量，在向量库里找最近的 $k$ 个。这个"找最近"是近似最近邻搜索，不保证精确，但比逐篇算快几个数量级。

所以稠密检索的成本分两块：离线编码全语料（每篇跑一次编码器），和在线编码查询 + 向量搜索。语料越大，离线成本越高；语料一更新，新增文档要重新编码。BM25 只需要倒排索引，构建和更新都便宜得多。

### 3.3 对比学习怎么训

编码器不是天生就会把"相关"的文本放近。它要用对比学习训练：给一个查询 $q$，一个相关文档 $d^+$（正例），若干不相关文档 $d^-$（负例），让 $q$ 和 $d^+$ 的相似度高于 $q$ 和 $d^-$ 的相似度。常用的损失是 InfoNCE：

$$
\mathcal{L}=-\log\frac{\exp\left(\operatorname{sim}(v_q,v_{d^+})/\tau\right)}
{\sum_{d\in\{d^+\}\cup\mathcal{N}}\exp\left(\operatorname{sim}(v_q,v_d)/\tau\right)},
$$

其中 $\mathcal{N}$ 是负例集合，$\tau$ 是温度，控制分布的尖锐程度。分子是正例相似度的指数，分母是正例加所有负例的指数和。训练让正例在分母中的占比变大，等价于让正例的相似度相对负例更高。

负例从哪来？最常用的是批内负例（in-batch negatives）：一个 batch 里有 64 个查询-文档对，对第 1 个查询来说，其他 63 个查询的正例文档都可以当负例。这样不用额外采样，计算效率高。缺点是可能有假负例：其他查询的相关文档，恰好也和当前查询相关，却被当成负例，给训练引入噪声。

训练数据从哪来？问答数据集（问题-答案段落）、搜索日志（查询-点击文档）、或用大模型合成。SAGE 没有训练检索器，它直接用现成的 gte-Qwen2-7B-instruct 和 ReasonIR。

### 3.4 双塔与交叉编码器

稠密检索通常是双塔：查询一个塔、文档一个塔，两边不见面，只算向量相似度。好处是文档可以离线编码，检索快；缺点是查询和文档的细粒度交互（比如"这个数字是否大于那个数字"）在各自编码时就丢了。

另一种是交叉编码器（cross-encoder），把查询和文档拼在一起过模型，直接输出一个相关性分数。它能看到两边的每个词，准得多，但每对(query, doc)都要跑一次模型，没法预先算，只能对少量候选做重排。这类模型叫重排器（reranker），比如 [DCI](../li2026-dci.md) 对比的 ReasonRank。它和检索器不是一回事：检索器负责从全库召回，重排器负责在候选里精排。

## 四、把 BERT 换成大模型：三种做法

"让检索器也会推理"不是一件事，是三个不同层面的技术。它们经常一起用，但改的东西不一样。

### 4.1 取隐藏状态：把 LLM 变成编码器

最直接的做法：拿一个 decoder-only 大模型（LLaMA、Qwen 这类，7B 到 8B 参数），把一段文本喂进去，取最后一层的隐藏状态，做平均池化或取最后一个 token，得到一个向量。这个向量就是句向量。

为什么可行？decoder-only 模型本来是为"预测下一个 token"训练的，但它的隐藏状态里编码了每个 token 在上下文中的语义。最后一个 token 的向量经过因果注意力，已经看过前面所有 token，可以当作整句的摘要。

为什么不能直接拿来用？因为预训练目标不是检索。模型没有学过"把相关文本放近、无关文本放远"，直接取出来的向量在语义相似度任务上往往不如 BERT。所以要用对比学习微调：拿一批(query, 正例文档, 负例文档)，按 3.3 的损失继续训练，改变模型权重（全参数或 LoRA），让它输出的向量适合检索。

还有一个架构问题：decoder-only 是因果注意力，每个 token 只能看左边。平均池化时，靠前的 token 看不到后面的内容，句向量会偏向开头。LLM2Vec 的做法是把因果掩码改成双向掩码，再加一个掩码下一 token 预测任务恢复模型的双向表示能力，然后做对比学习。GritLM 把生成和嵌入统一到一个模型里，同一个模型既能生成文本，也能输出句向量。gte-Qwen2-7B-instruct 基于 Qwen2-7B，用多阶段对比学习训练成嵌入模型。

代价是编码成本：BERT-base 只有 1.1 亿参数，7B 模型大 60 多倍；编码一篇 13,000 token 的论文，要跑一次 7B 前向。20 万篇论文就是 20 万次。这就是 SAGE 里"稠密索引比 BM25 贵"的具体来源。

### 4.2 指令微调：让一个编码器适配多种任务

同一个查询，在不同任务里该找什么，是不一样的。"Python"在代码检索里要找 Python 代码，在论文检索里要找关于 Python 的论文，在新闻检索里要找提到 Python 的新闻。通用的句向量会把它们编码成差不多的向量，因为字面一样。

指令微调的做法是：在查询前面加一句任务说明，把任务信息也喂给编码器。训练数据长这样：

```text
Instruct: Given a scientific paper search query, retrieve relevant papers
Query: ICML 2023 symbolic regression ODEFormer Feynman

Instruct: Given a code search query, retrieve relevant functions
Query: parse JSON file
```

模型在训练时见过大量"指令 + 查询"的组合，学会根据指令调整编码方式。推理时也必须用同样的模板：先写指令，再写查询。如果只给查询、不给指令，模型看到的输入分布和训练时不一样，效果会下降。

这里有一个容易误解的点：指令微调不是"推理时随便加一句提示词就变强"。指令是训练分布的一部分；训练时见过，推理时复现，才有效。代表模型是 Promptriever（把指令训练进检索器）、gte-Qwen2-instruct（支持指令前缀）。SAGE 用的 gte-Qwen2-7B-instruct 名字里的 instruct 就是指这个能力。

指令微调的代价是：查询必须按训练格式写。agent 生成的子查询是关键词串，没有指令前缀，也不一定符合模型训练时见过的问句形式；这就埋下了 SAGE 说的"查询-检索器错配"。

### 4.3 推理链扩展查询：先想清楚，再检索

前两种做法改的是编码器；这一种改的是查询。

流程是：用户给一个短查询 $q$，先用一个生成模型把 $q$ 扩写成一段长文本 $q'$，里面包含推理步骤、可能的答案形式、相关概念；再用编码器编码 $q'$，去检索。例如：

```text
原查询：ICML 2023 symbolic regression ODEFormer Feynman

扩写后：I am looking for a paper published at ICML 2023 about symbolic
regression. It likely builds on AI Feynman and ODEFormer. The paper may
use physics-informed heuristics to search expression trees...
```

扩写后的文本更长，包含更多语义线索，稠密编码器更容易匹配到相关文档。这类方法叫查询扩展（query expansion），代表是 HyDE（先让模型生成一段假设答案，再用假设答案的向量去检索）和 Query2Doc（先生成伪文档，再检索）。

SAGE 对比的 ReasonIR 不属于这一类。它是用推理密集型数据训练的稠密检索器：训练数据里的查询本身就需要多步推理，模型学会把这类查询编码到合适的位置；检索时它仍然直接编码查询，不在查询时生成推理链。SAGE 把它叫 reasoning-intensive retriever，原因在此。

查询扩展的代价有两个。第一，查询时多了一次生成模型调用，延迟和成本都增加。第二，扩写可能引入错误概念：如果生成模型把 "physics-informed" 当成核心线索，而真正的答案是符号回归，扩写就会把检索带偏。SAGE 的 Fig. 4 是一个相关的失败，但原因不同：ReasonIR 没有做扩写，它是在编码时把标题里的 "physics-informed" 当成了主要线索，反复召回物理信息神经网络的论文；BM25 被 `ODEFormer`、`AI Feynman`、`ICML 2022..2024` 这些词面锚点拉住，没有漂移。两者都说明同一件事：把语义压成一个向量，细粒度的词面约束容易被丢掉。

### 4.4 三者关系

| 做法 | 改什么 | 代表 | 主要代价 |
| --- | --- | --- | --- |
| 取隐藏状态 | 模型：把 LLM 改成编码器 | LLM2Vec、GritLM、gte-Qwen2 | 编码一篇文档要跑一次 7B 前向 |
| 指令微调 | 训练目标与输入格式：让一个模型适配多任务 | Promptriever、gte-Qwen2-instruct | 查询必须按指令模板写 |
| 推理链扩展查询 | 查询：先扩写再编码 | HyDE、Query2Doc | 多一次生成调用，可能语义漂移 |

三者可以叠加。gte-Qwen2-7B-instruct 是"取隐藏状态 + 指令微调"；ReasonIR 是"取隐藏状态 + 推理密集型训练数据"，它不在"推理链扩展查询"这一列。SAGE 的对照组里，gte-Qwen2-7B-instruct 与 ReasonIR 都是稠密检索器，区别在训练数据和是否支持指令。

## 五、为什么这套东西到了 agent 场景可能失效

SAGE 的论点是：这三种技术都依赖一个假设——查询的语义可以被压成一个稠密向量，而且推理时的查询形式与训练时一致。agent 生成的子查询是关键词串，这个假设会在四个地方出问题。

第一，稀有词被稀释。稠密编码器把整串查询压成一个向量，`ICML`、`2023`、`ODEFormer` 这些词只占向量里很小的一部分；语义上更"重"的 `symbolic regression`、`physics-informed` 会主导相似度。BM25 对每个词独立计分，稀有词的 IDF 高，权重反而大。所以同一个查询，BM25 会抓住 `ODEFormer`，稠密检索器可能抓住 `symbolic regression`。

第二，长文档被截断。稠密编码器有最大输入长度，比如 8K、32K token；超过的部分直接丢掉。SAGE 的论文平均 13,376 token，长论文可能超过 32K；BM25 索引全文。如果证据落在文档后半部分，稠密检索器根本看不到。这不是"语义能力"的问题，是"输入窗口"的问题。

第三，指令模板缺失。gte-Qwen2-7B-instruct 训练时见过 "Instruct: ... Query: ..." 的格式；如果 SAGE 直接拿关键词串去编码，没有加指令，模型看到的分布和训练时不一样。SAGE 没有写它怎么调用 gte 和 ReasonIR（是否加指令、文档侧是否加前缀），这是一个可复现缺口，也是"BM25 更强"的一个替代解释。

第四，语义漂移。稠密编码器把查询压成一个向量，向量里的主导概念可能不是真正要找的东西。SAGE 的 Fig. 4 是一个单例：ReasonIR 把标题里的 "physics-informed" 当成了主要线索，反复召回物理信息神经网络的论文，越查越偏。

这四点合起来，就是 SAGE 的问题：不是"稠密检索不好"，而是"稠密检索的训练假设和 agent 的查询形式不匹配"。换一个更强的编码器不一定解决，因为问题出在接口形状，不是模型能力。

## 六、读论文时的检查清单

看到一篇论文说"我们用稠密检索"或"LLM-based retriever 更强"时，按下面几项核对，能判断它的结论能推广到哪：

1. **编码器是什么**：BERT、7B LLM、还是 API embedding？参数量决定编码成本。
2. **维度与最大输入**：向量多少维、文档截断到多少 token。长文档任务要特别看截断。
3. **训练数据**：查询是自然语言问句、关键词串、还是搜索日志？训练分布决定它对 agent 查询的适应性。
4. **推理时有没有加指令模板**：加了什么指令、文档侧有没有前缀。没加就可能低估模型。
5. **有没有做查询扩展**：扩写模型是什么、扩写几次、失败时怎么回退。
6. **索引与距离**：FAISS/HNSW、余弦还是内积、是否归一化。
7. **与 BM25 的对比是否同预算**：同语料、同 top-$k$、同文档截断、同查询格式。很多"稠密更强"的结论在这些条件不一致时会反转。
8. **文档长度分布**：短文档、答案靠前的语料有利于只编码前缀的稠密模型；长文档、证据分散的语料有利于 BM25。

## 七、和仓库其他笔记的关系

- [SAGE](../hu2026-sage.md)：在 20 万篇论文上比较 BM25、gte-Qwen2-7B-instruct、ReasonIR，发现 BM25 在短答案题上相对高约 29%。这篇概念笔记解释它为什么可能发生，以及它的对比里有哪些口径要核对。
- [A-RAG](../du2026-a-rag.md)：没有抛弃稠密检索，而是把句子级向量检索做成 `semantic_search` 工具，让 agent 自己决定查几次、查什么粒度。
- [DCI](../li2026-dci.md)：把稠密检索整个去掉，直接用 `grep` 在原始语料上做词面匹配；它的"定位度"优势可以理解为 BM25 式词面精度加上文件内部的继续操作。
- [DecisionRAG](../wan2026-decision-rag.md)：用决策模型逐层选分支，候选集由树结构给出，不依赖稠密检索的 top-$k$ 排序。
- [STAIR](../kumar2026-stair.md)：用目录叶节点当检索单位，把"文档级稠密检索"换成"结构级标题生成"，绕开了长文档截断问题。
