# 失败归因：为什么最后一步看不到病因

这篇不是论文笔记，是一篇概念说明。它展开的是 [OAT 笔记](../yeh2026-oat.md) `Why` 里的两句话：错误会被后续步骤部分补偿，所以只看最后一步看不出最早的偏差；以及这种诊断成本会卡住部署、调试与审计。那两句为了控制篇幅压得很紧，这里把"补偿"和"卡住"各自拆开，并补上几个具体的失败场景。

## 一、先把四个东西分开

一次 agent 运行叫一条轨迹：收到问题 $Q$，反复"决定动作 → 调工具 → 拿到结果"，直到交出答案。围绕这条轨迹至少有四个不同的东西，日常说话却常把它们混成一句。

- **结果**：任务成没成，通常由评测函数 $Z(\tau)$ 判定，成功为 1，失败为 0。
- **最终答案**：用户看到的那段输出，附在轨迹末尾。
- **错误步**：真正把任务推向失败的那一步或几步。
- **失败归因**：给定一条失败轨迹，找出错误步的集合。

"这次失败了，答案是错的，最后一步有问题"——这句话把三件事说成了一个。实际关系是：结果是结果，答案是表现，错误步是原因。三者在轨迹里的位置可以完全不同：答案总在最后，原因可以在第 3 步，中间还隔着十几步看起来正常的操作。

这里要区分两个任务。**检测**回答"这次运行失败了没有"，通常不难：有 rubric、有单元测试、有人看一眼就能判。**归因**回答"哪一步导致的"，很难：失败轨迹有几十上百步，每一步单独看都可能是合理的。论文引用的 Who&When 基准里，最强的推理模型定位错误步的准确率不到 15%（§1），说明"把日志丢给一个聪明模型"并不能解决归因。

论文对"错误步"给了一个可操作的定义（Def. 3.1）：这一步的动作在给定问题和前缀时确实是错的（幻觉、错误工具调用、没处理工具报错），并且这个错误之后没有被纠正、最终促成了失败。它刻意不用"只改这一步就能救回任务"的反事实定义，因为复杂任务常常是多步错误叠加，单点修复本来就不成立；标注者也拿不到那个正确的替换动作，无法验证。

## 二、"被后续步骤部分补偿"具体指什么

Agent 的执行是一个循环，不是一次生成。第 $t$ 步出了错，后面还有 $t+1$、$t+2$……这些步骤会继续跑，而它们的目标是"把任务做完"，不是"检查前面有没有错"。于是出现三种典型的掩盖。

```mermaid
flowchart LR
    A["第 3 步<br/>检索返回空<br/>模型凭记忆补答案"] --> B["第 4 步<br/>用错误实体查下游信息"]
    B --> C["第 5 步<br/>工具正常返回"]
    C --> D["第 6 步<br/>答案格式完整、数字自洽"]
    D --> E["用户看到：一个合理的错误答案"]
    A -. "病因在这里" .-> E
    D -. "人却容易从这里往回找" .-> E
```

**第一种：前提污染。** 第 $t$ 步把实体、数字或日期弄错，后面所有步骤都建立在这个错前提上，但每一步自身逻辑完全正确。比如 agent 把"宾夕法尼亚医院"当成美国最古老的医院，下一步去查这家医院附近的充电桩——查充电桩这一步会成功，返回的地址也真实存在，只是这个地址回答的是另一个问题。错误没有被纠正，只是被"继承"了。

论文 Fig. 2 就是这种形态：第 6 步维基检索返回空，第 7 步模型凭记忆给了一个医院名，第 8 步用这个医院名查充电桩、工具正常返回，第 9 步组装答案。最后一步的推理是通的：医院是真的，充电站地址也是真的，句子也没有语法问题。原文对它的评价是"internally coherent while being contingent on the erroneous prior step"——内部自洽，但依赖一个错误的前置步骤。

**第二种：局部修复。** 工具报错、检索返回空、代码抛异常，agent 重试、换关键词、换工具，或用 `try/except` 兜住，最后"跑通了"。表面上的错误信号消失了，但数据来源已经换成模型记忆、过期缓存或不可靠的替代源。任务还在往错的方向走，日志里却不再有红色报错。这一步也很难被标成错误：重试本身是合理策略，失败的是"重试之后接受了什么"。

**第三种：覆盖重写。** agent 自己说"let me reconsider"，把前面算出的错误中间值覆盖掉。最终上下文里只剩下看起来正确的最终值，错误值只留在完整轨迹里。如果你只看最后一条 assistant 消息，根本不知道它曾经出现过。

这三种形态有一个共同点：**任务仍然失败，但失败的痕迹被抹掉了一半。** "部分"这个词就是这个意思——补偿很少能真的把任务救回来，否则 $Z(\tau)=1$，任务就成功了；但它足以让错误在表面上变得不可见。反过来，如果错误一点没被补偿（工具直接报错、代码直接崩溃），归因反而容易，因为信号还留在原地。

还要看到，这种补偿不是 agent 故意的，而是它被设计成有韧性的自然结果。重试、退化到备用方案、重新规划、把失败包装成一段解释，都是提高任务成功率的常用手段；它们同时抹掉了错误信号。**系统的鲁棒性和可观测性在这里是冲突的**：越能自己兜底，越难被外部看出兜过底。

## 三、为什么"看最后一步"会稳定地看错

人读日志天然从后往前，因为最后一条消息就是用户看到的答案。这个习惯在传统软件调试里也常见：看到崩溃栈，就先怀疑栈顶那一行。但崩溃栈至少指向了崩溃发生的位置，agent 的失败连这个位置都不给。

**第一，最后一步通常只是"把已经错的东西说出来"。** 论文 App. H.2 Case 1 里，agent 从第 5 步到第 15 步一页页翻 pull request，第 16 步说"没找到 #62091"。看起来错误在第 16 步，实际上第 16 步只是症状：真正的问题是它选了"逐页翻完"这个策略，而目标 PR 的编号范围早就和当前页面对不上。模型在第 16 步只是把前面十几步累积的无效搜索总结成一句话。

**第二，错误步往往长得很正常。** 它常常不是报错，而是一次成功的工具调用、一段通顺的推理、一行能跑的代码。传统调试可以 grep stack trace、看非零退出码；agent 的失败大多不抛异常——工具正常返回（只是返回空）、模型正常生成（只是内容错）、格式正常（只是实体错）。"找报错"这类启发式在这里直接失效。

**第三，正确的后续会把错误稀释掉。** 论文 Fig. 14 里，第 7 步按显示名而不是邮箱统计评论数，把两个同名用户合并；第 8 步基于这个错误计数写下代码；第 10 步返回错误的人。第 8、10 步单独看都是合法代码、合法推理，只有把第 7 步的语义拿出来对照，才知道它们继承了一个错的前提。论文的案例里，异常分沿着传播链逐渐衰减，原因也在这里：继承错误比引入错误"更正常"。

**第四，看起来奇怪的步骤不一定错。** 论文 App. E 专门处理了探索式搜索：agent 换关键词多查几次是正常策略，第一次失败不算错；只有重复同一查询、拿到同样结果还继续重复，才把之后的每一次标成错误。也就是说，"这一步看起来可疑"和"这一步导致失败"是两件事，前者会把大量正常探索误判成错误。

所以归因需要的参照系不是"哪一步像错误"，而是"一次正常推进到这里应该是什么状态"。这正是 OAT 选择用成功轨迹学"正常动力学"、而不是训练一个错误步骤分类器的原因：判断依据是偏离，不是异常事件。

## 四、为什么会卡住部署、调试、审计

"卡住"不是"系统跑不起来"，而是"不能放心地扩大规模"。三件事要的东西不一样，但都依赖同一个前提：知道是哪一步出的问题。

| 活动 | 要回答的问题 | 缺少步级归因时会发生什么 |
| --- | --- | --- |
| 部署 | 能不能放出去、要设什么护栏 | 只能整体人工复核，或者干脆不上线 |
| 调试 | 改哪里、改完是否真的修好 | 只能整体换模型或改提示，无法做针对性回归 |
| 审计 | 哪一步、哪个 agent、依据什么做的决定 | 复盘只能写"模型偶尔会错"，无法交代 |

**部署**要回答"能不能放给真实用户"。这需要三样东西：失败率可接受、失败模式已知、有对应的护栏。护栏必须具体到机制，比如"某搜索 API 超时就禁止直接作答""检索为空时必须显式说不知道"。这些规则只有在知道失败模式时才写得出来。如果每次失败都要专家花几小时定位，团队在发布前就无法判断"这次失败是偶发还是系统性的"，也无法把失败按类型聚合成一张可行动的清单。

更麻烦的是，高风险场景里的错误常常看起来是对的。写代码时，一个能通过测试但语义变了的补丁——比如把 `>` 改成 `>=`，而测试没覆盖边界——最后一步是"输出 diff 并提交"，读起来完全正常；做科研时，一条格式、作者、年份都像真的、实际不存在的文献，最后一步是"生成综述段落"，读起来也完全正常。错误越隐蔽，人工复核越难发现问题，逐条复核的成本又会让"用 agent"在经济上不成立。结果是要么不敢上线，要么上线了但没人知道它在哪些情况下会错。

**调试**要回答"改哪里"。归因给出的是具体的修改对象：是提示词没教它处理工具报错，还是重试策略有问题，还是规划器选了低效策略。没有步级归因，只能整体换模型、整体改提示；改完也不知道是不是修好了那个具体的失败模式，因为没有定位就没有针对性的回归测试。论文在 MCP-Atlas 上人工标了 88 条失败轨迹的步级错误，正是为了让"改哪里"这件事可测量。

**审计**要回答"出了事怎么交代"。审计关心的不是"失败了没有"，而是"哪一步、哪个 agent、依据哪条工具返回做了这个决定"。代码合并错了、研究报告引用了不存在的文献，事后要复盘、要定责、要向合规或客户解释。没有可复现的步级记录，复盘只能写成"模型偶尔会错"，这在受监管的场景里过不了关。

再把这个"瓶颈"量化一下。下面的数字是假设，不是论文数据：一天 1,000 次运行，失败率 5%，就是 50 条失败；每条人工定位 1 小时，就是 50 人时/天，需要 6 个全职专家只做分诊。而且这是事后工作——等定位完，用户早就拿到错误答案了。失败率不变的情况下，系统规模越大，诊断越跟不上。所以瓶颈不在"模型会不会做任务"，而在"没有人能解释它为什么做错"；解释不了，扩容、上线、迭代就一起被卡住。

## 五、这套说法覆盖不到什么

**不是所有失败都有"那一步"。** 环境或基础设施故障就不在 agent 行为里：论文从 100 条失败里剔除了 12 条，理由包括某个搜索 API 固定超时、日志为空（App. D）。这类失败的归因对象是工具或网络，不是某一步决策。任务本身有歧义、或者评测函数判错了，也不属于失败归因要解决的问题。

**不一定只有一步。** 复杂任务常见多步错误叠加，论文的定义因此输出一个集合而不是单个下标；平均每条失败轨迹有 1.56 个错误步，最多 12 个（Table 4）。"根因只有一处"是一个方便但不总是成立的假设。

**归因不等于因果。** 异常分高只说明"这一步不像正常推进"，不保证它是失败的原因；反过来，不是每个因果错误都会表现为异常。要确认因果，需要干预或反事实——把这一步换掉、重放后续，看任务能否恢复；但在长任务里，重放环境的代价很高，这正是论文放弃反事实定义、退到"异常即代理信号"的原因，也是它自己在 §A 承认的局限。

**步级之外还有 agent 级。** 多 agent 系统里，"第 7 步错了"和"第 7 步是 agent B 做的"是两个不同粒度的结论。前者回答流程哪里断了，后者回答责任与协作结构哪里出了问题；后者往往才是改系统时真正要动的对象。

## 六、和 OAT 的关系

理解了上面这些，就能看出 OAT 的几个设计不是随意的。因为错误信号不是"出现了异常事件"，而是"偏离了正常推进"，所以它用成功轨迹学一个正常动力学模型，把每步的重建误差当异常分；因为步级标签贵且歧义，所以训练完全不碰失败轨迹；因为错误可能在推理内容里而不在最终输出里，所以它用生成动作时的隐状态而不是文本。

但异常分只是代理信号，不是因果结论。论文自己的案例里，它会漏掉早期的隐式推理错误（"我没有合适的工具"在成功轨迹里也会出现），会被全局硬阈值压掉刚好低于 $\delta$ 的弱错误，也会把"局部正常、整体低效"的规划错误摊成一段缓慢升高的分数而不是尖峰。更细的评测问题（基线强度、CORAL 口径、标签自产）写在 [OAT 笔记](../yeh2026-oat.md) 的 `Ideas` 里，这里不重复。
