# Agent-Diff: Benchmarking LLM Agents on Enterprise API Tasks via Code Execution with State-Diff-Based Evaluation

## Why

企业里大量工作是通过 SaaS 的 API 完成的：在 Slack 里建频道、发消息，在 Box 里挪文件、打标签，在 Linear 里建工单、改状态，在 Google Calendar 里排会议、查空闲。让 agent 做这类事，主流做法是把每个 API 包成一个结构化工具（JSON schema 描述参数），由模型逐个调用。这条路线在工具目录长到几百上千个时会失效：模型光读工具描述就吃满了上下文，而且每加一个接口就要人写一份 schema。更省的做法是**让 agent 直接写代码**（Bash 加 `curl`，或者 Python SDK），在代码里完成"查—判断—改"的循环（§1）。

要评这类 agent，评测设计必须同时满足三个要求：环境要真（接口形状、错误码、分页、权限都像生产系统）、可复现（同一次提交跑两次结果一样）、能判对错（不靠人看）。现有基准各缺一块。**模拟环境**（API-Bank、MCP-RADAR、FuncBenchGen）可控但接口形状被简化，模型学到的调用方式在真实系统上不成立。**接真实服务**（MCP-Bench、MCP-Universe）真实但不可复现：服务端数据会变、时间戳会变、限流会变，ground truth 要现场取。**容器化环境**（SWE-Bench、Terminal-Bench、MCPWorld）可复现，但前两个评的是源码补丁或命令行任务的测试通过，不是企业 SaaS 的状态；MCPWorld 要开白盒插桩，闭源 SaaS 做不到（§2、Table 1）。

判分方式同样有机制层的缺口。**轨迹匹配**（要求调用序列与期望一致）对等价的替代路径过于苛刻，也不保证状态真的变了。**目标状态比对**（τ-Bench 的做法）只看"该变的那条记录变了对不对"，看不到"顺手也改了别的"。**响应比对**（把 agent 的 API 返回值与一次 ground-truth 执行的返回值做差）只验证返回值，不验证状态。**LLM 裁判**（MCP-Bench）有随机性，也容易被措辞影响。这四种方式里，只有一种能同时回答"该变的变了没有"与"不该变的动了没有"，而它需要拿到**完整的环境状态**，不只是目标记录（§2）。

为什么现在必须解决：企业 SaaS 的任务大多是多步、跨服务、带信息缺失的。一步错就会把错误带到后面——先搜错了文件、再基于错的 ID 打标签、最后把标签打到了同一个目录里的另一份文档上。这类错误在最终回复里完全看不出来，而在真实业务里就是数据事故。评测如果只看"agent 说做完了"，等于把这类事故计为成功。

于是问题落到这里：能不能既不接真实服务、又能保留真实接口形状，还能用完整状态差分判定"改对了没有、有没有多改"？如果这样做，头部模型在"必须自己探接口、自己找 ID"的任务上还能拿多少分？给不给 API 文档，又会让分数怎么动？

## What

论文的答案是：能。做法是给四个企业 SaaS（Slack、Box、Linear、Google Calendar）各做一份**容器化的接口副本**——形状、错误码、分页都一样，数据存在独立 schema 的 PostgreSQL 里；agent 在 Bash 里写代码发请求，所有流量被拦截到本地副本；评测用**状态差分契约**：把任务前后的实体表快照做差，得到新增、删除、修改三组变化，再用声明式断言核对，并用**闭世界不变量**把"没有被断言解释的改动"一律判为副作用（§3、§4）。在这套装置上给出 224 道题，测 9 个模型，无文档条件下断言加权分从 38.0 到 88.1（Table 4）。

先把任务说清楚。输入是一句自然语言请求（可能不给全标识符）加一份初始沙箱状态；agent 只有 Bash 与一个容器，可以 `curl`、可以 `jq`、可以写脚本，所有网络请求被路由到本地副本。输出是这份请求在环境里造成的**状态变化**，以及两个判定：`Pass`（二值：没有副作用且所有断言成立）与 `Score`（断言加权：通过断言数除以断言总数，但只要有副作用就整题记 0）（§4、Eq. 11–13）。边界是四个服务的 108 个接口、单轮任务、无用户对话；不含多轮澄清、不含人工审批流、不含跨服务事务。

### 新认识：判"做了什么"要比判"怎么做的"更稳

第一个认识是**过程与结果必须分开**。轨迹匹配把"用哪个接口、按什么顺序"当成正确性的一部分，但企业任务里同一条路径往往有多种合法走法：先 `GET /folders/0` 列目录再定位，与先 `GET /search?query=` 再取，结果可以完全相同。状态差分只问"终态差是什么"，因此能接受任意合法路径，同时因为看的是**全表**差分而不是目标记录，还能抓住"改了不该改的"。`[已验证：§4 的形式定义 + Fig. 2 的对照]`

第二个认识是**副本只需要在"被用到的请求集"上等价**。真实服务内部还有通知、分析、缓存这些副作用，agent 看不到，对评测也无意义，因此不必复刻。论文把这一点写成定义：定义 $\mathcal{R}^*$ 为基准任务实际会用到的请求集合，只要副本 $\hat{f}$ 在 $\mathcal{R}^*$ 上与生产 $f$ 行为一致，就足以支撑评测（Eq. 1）。这个简化是整套方案成立的前提，也是它最大的可攻击点——见 Ideas 第二条。`[已验证：Eq. 1 的形式定义；保真度证据只有定性描述]`

第三个认识是**"近期新增的接口"可以当一个天然实验**。Box 在 2025 年 7 月上线了 Hub 接口，一批被评测模型的训练截止在这之前，因此 Hub 相关的题考的不是"记不记得 API"，而是"能不能在读文档后现场学会"。实测结果支持这个解释：无文档时 Hub 题几乎全军覆没，给相关文档后提升 +19.0 个百分点，而非 Hub 题只提升 +3.4（Table 6）。`[已验证；训练截止未逐个模型核实，见 Ideas 第五条]`

### 新方法：容器副本 + 状态差分契约 + 闭世界不变量

第一样方法是**接口副本**。每个服务被建成一个"有状态的机器"：状态 $S$ 是从公开接口规格推导出的关系型数据库，实体类型（Slack 的 User、Channel、Message；Box 的 File、Folder）直接映射成表；所有操作归约为插入、更新、删除三种转移（Eq. 2–4）。副本的构造信息全部来自公开材料：OpenAPI 或 GraphQL introspection 给出的实体模式、官方文档给出的操作语义、官方 SDK 的类型定义给出的返回格式、以及文档化的错误码。REST 服务（Slack、Box、Calendar）用 OpenAPI 加 SDK 推导 schema；GraphQL 服务（Linear）解析 introspection 并去规范化成外键关系（§3.1、§G）。`[§3.1]`

第二样方法是**状态差分**。执行前快照所有实体表 $T_{\text{before}}$，执行后再快照 $T_{\text{after}}$，算三组差：

$$
\Delta_{\text{add}}=T_{\text{after}}\setminus T_{\text{before}},\quad
\Delta_{\text{del}}=T_{\text{before}}\setminus T_{\text{after}},\quad
\Delta_{\text{mod}}=\{(x,x'):x.\text{pk}=x'.\text{pk}\ \wedge\ x\ne x'\},
$$

其中 $\text{pk}$ 是主键。得到的差分再与任务声明的期望变化比对（Eq. 5–7）。`[§3.1]`

第三样方法是**声明式断言加闭世界不变量**。每条断言声明四件事：差分类型（新增/删除/修改）、实体（表）、字段级约束（相等或子串匹配）、期望条数（§4）。闭世界不变量是这套判分的核心：设 $A(\tau)$ 是任务的必需断言集合、$F(\tau)$ 是被显式忽略的字段（例如 `updated_at` 这种非确定性时间戳），那么差分里的每一处改动，要么能被 $A(\tau)$ 里的某条断言解释，要么只涉及 $F(\tau)$ 里的字段；否则一律判为副作用，整题失败（§4）。这条规则把"没被要求但发生了"从"不计分"提升为"判错"，代价是它要求任务作者穷举所有合法改动。`[§4]`

第四样方法是**每环境独立的数据库 schema**。每次运行从一个模板种子出确定的初始状态，每个环境在自己的 schema（`state_{env_id}`）里跑，因此并发执行不会互相污染，同一道任务跑两次的初始状态严格相同（Eq. 8）。这条是重复测量与可比性的前提。`[§3.1]`

### 新结论：分数区间、文档效应与失败结构

**榜单（无文档）。** DeepSeek-v3.2 88.1±2.4、Devstral-2512 86.0±3.1、Qwen3-VL-235B 79.2±3.3、Kimi-K2-0905 75.4±3.5、Grok-4.1-Fast 74.9±2.7、Gemini-3-Flash 73.8±3.7、GPT-OSS-120B 68.5±4.1、Claude-Haiku-4.5 49.3±5.5、Llama-4-Scout 38.0±4.1（Table 4）。头两名与第三名之间有约 7 分的断层，尾部两个低于 50。`[已验证]`

**文档效应分裂。** 给相关文档后，通过率提升 +7.0±2.3 个百分点（$P=1.00$），但断言加权分只提升 +2.4（$P=0.73$，不显著）；给全部四个服务的文档，通过率仍提升 +6.8 个百分点，分数只 +0.2（$P=0.53$），而在 Linear 上分数反而降 4.0（Table 5）。论文的解释是：文档帮 agent 把简单任务整题做对（二值指标看出来），但在需要多条断言都成立的大任务上收益递减；无关文档会挤占注意力。`[已验证；"挤占注意力"是解释不是测量，见 Ideas 第四条]`

**Hub 题作为新颖性实验。** 相关文档让 Hub 题提升 +19.0±10.5（$P=1.00$），非 Hub 题 +3.4±4.4（$P=0.93$），"Hub 提升大于非 Hub"的后验概率 0.999。分层看，DeepSeek 与 Devstral 在 Hub 题上各提升约 31 分，在非 Hub 题上基本不动（Table 6）。`[已验证]`

**失败结构。** 抽 4,032 条轨迹（9 模型 × 224 题 × 2 种文档条件）用 LLM 裁判标 31 种细粒度错误，合并成 6 类：工具使用、没有改状态的动作、用户诉求未解决、状态更新错误、幻觉、不完整执行。给文档后各类错误的**发生率**都下降，降幅最大的是推理失败 −25.9 个百分点与幻觉 −21.2；**恢复率**也都上升，参数错误 +21.3、推理失败 +20.8；而"不完整执行"在两种条件下恢复率都是 0.0%（§6.3）。`[已验证；标注由 LLM 完成，无人工一致性，见 Ideas 第七条]`

## How

判型：以**实证与基准类**为主，附**系统与算法类**。实证与基准类的依据是核心产出是 224 道可执行任务、一份判分契约、9 个模型 × 3 种文档条件 × 3 次重复的测量；系统与算法类指三样基础设施——接口副本、流量拦截与 schema 隔离、差分与断言引擎。没有新模型、没有训练。

### 一、任务怎么造：先定难度分布，再生成，再人工调

任务难度主轴是**时域** $n^*(\tau)$，定义成"在最优策略下最少需要几次接口调用"。$n^*$ 不是事后统计的，而是生成时先抽出来的：从 $\{1,\dots,40\}$ 上的平移截断指数分布采样，$\Pr[n=k]\propto e^{-\lambda(k-1)}$，目的是得到一条重尾分布——大部分任务短、少数任务很长。生成与人工筛选之后，实际分布的均值是 5.3、范围 1–24，比目标分布略高，因为"过于简单"的提议被剔掉了（§3.2、Eq. 9）。

给定服务 $s$ 与目标时域 $n$，从该服务的接口集 $\mathcal{E}_s$ 里均匀独立地抽 $n$ 个接口，得到一个期望调用的多重集合（Eq. 10）。均匀抽样保证了覆盖面：最终跨 108 个接口，Box 27、Slack 25、Linear 19、Calendar 37。这个多重集合决定了任务的两个结构维度——**操作画像**（搜索/创建/读/更新/删除，不互斥）与**实体范围**（单实体还是多实体）。另外两个维度在生成与人工环节控制：**信息可得性**（标识符是给在提示里，还是要 agent 自己查）与**歧义度**（提示对目标的指代有多模糊，低/中/高三档）。

生成用两个模型（Claude Opus 4.5 与 Gemini 3 Pro）产出三样东西：一句自然语言请求、一份确定性种子模板（定义初始状态 $S_0$）、一组声明式断言（描述期望差分与禁止副作用）。有些任务人工先写好种子，只让模型写请求与断言；有些三样一起生成（§3.2）。生成之后人工审：确认标识符确实能查到、需要的接口与权限确实存在，然后人为降级提示词来调歧义度（删掉显式标识符、加入笔误变体、在初始状态里加干扰实体）。

最终 224 道题的结构：搜索类 80%、创建 73%、更新 66%、读 55%、删除 26%；单实体 105、多实体 119；显式信息 77、隐式 147（即 66% 的任务要求 agent 自己查标识符）；歧义低 101、中 103、高 20（Table 3）。四个服务的题量是 Box 48、Slack 59、Linear 57、Calendar 60，时域均值 4.6、5.6、5.2、5.9。

### 二、副本怎么建，保真度怎么验

对每个服务，先用 OpenAPI（Slack、Box、Calendar）或 GraphQL introspection（Linear）把实体抽出来，一个实体一张表，字段类型与可空性照抄；Linear 的嵌套实体要拆成多张表加外键。然后为每个接口实现请求解析、参数校验、状态转移、响应渲染、错误码。

保真度用两条路验。第一条是**自动一致性测试**：对每个已实现的接口，向生产 API 与副本发同样的请求，比对返回 JSON 的结构（键、类型、分页格式、错误码）。第二条是**对抗探测**：用一个辅助 LLM agent 系统性地向生产 API 发边界请求（非法参数、缺失字段、边界值），把暴露出来的未文档化错误条件补进副本（§G）。论文没有报告这两条路的量化结果——多少接口通过、多少不一致、怎么处理不一致。

有一条明确的设计取舍：内部副作用（通知、分析、缓存）不复刻。理由如前所述，它们在 agent 的观测面上不可见。但这意味着"检出了副作用"这个能力的作用域是**被建模的表**，不是整个系统。

### 三、判分：两个指标与一个不连续点

`Pass` 是二值：$ \text{Pass}(\tau)=\text{clean}(\tau)\cdot\mathbb{1}[\forall a\in A(\tau),\ \text{sat}(a,\Delta_S)=1]$。`Score` 是断言加权：$s(\tau)=\text{clean}(\tau)\sum_{a}\text{sat}(a,\Delta_S)$，分母是断言总数 $m(\tau)=|A(\tau)|$；聚合时按断言数加权，$\text{Score}(\mathcal{T})=\sum_\tau s(\tau)/\sum_\tau m(\tau)$（Eq. 11–13）。

这里有一个容易被忽略的性质：`clean` 是乘在前面的，所以一个任务只要有一处未被解释的改动，无论断言对了几条，都记 0。这让 `Score` 在两个任务之间不可比——同样是 0.8 分，可能是"五条断言对了四条、没有副作用"，也可能是"十条断言对了八条"；而"四条全对但多改了一条记录"和"一条都没对"在数值上完全一样。论文用这个不连续性换"副作用零容忍"，在方法上说得通，但读者需要知道 0 分的构成有两种完全不同的原因。

区间用任务级贝叶斯自助法：对 224 道题抽 10,000 次 Dirichlet 权重，每次算加权分，取后验均值与 95% 可信区间（Eq. 14）。文档消融用配对版本：同一次 Dirichlet 抽样同时作用于两个条件，得到 $\Delta^{(b)}$ 的后验，报告 $\Pr[\Delta>0]$（§A.1、§A.2）。

### 四、实验：一个 ReAct 外壳，三档文档

一次性交互：系统提示要求模型先推理再输出一个 Bash 代码块，代码块被执行，输出回填，循环。终止条件是模型输出 `<done>`、轨迹到 40 轮、或墙钟超时 8 分钟。所有模型走 OpenRouter，用各家默认温度，用满上下文窗口，超限直接判失败。

三档文档条件：无文档约 400 token（只给服务名、base URL、ReAct 指令），相关文档约 3,200–10,000 token（目标服务的接口规格），全文档约 22,300 token（四个服务的规格都塞进去）。每个（任务，条件）跑 3 次，因此每个模型 224×3×3=2,016 条轨迹（§5.1）。

### 五、走一遍：一个 Hub 任务的两条路径

Fig. 2 给的是"整理研究资料 Hub"这道题，$n^*=3$。无文档时，Claude-Haiku-4.5 的五步是：列根目录（`GET /folders/0`）、列目录内容（`GET /folders/{id}/items`）、尝试 Collections 接口（`PUT /files/{id}`，返回 null）、查 collections（`GET /collections`，只有 "Favorites"）、然后**声称完成**。它走的是 Box 里存在但不适用的旧接口，而且最后一步把自己骗过去了。

给相关文档后，同一条请求变成：直接建 Hub（`POST /hubs`）、搜到目标文件夹（`GET /search?query=...`）、列目录项、把文件加进 Hub（`POST /hubs/{id}/manage_items`）、再读回来确认（`GET /hub_items?hub_id=...`）。终态正确，判定通过。

这个例子说明文档起作用的方式不是"告诉模型有这个接口"，而是"告诉模型该用哪个接口、以及调用之后怎么确认"。它也解释了为什么 Hub 题提升 31 分而非 Hub 题几乎不动：非 Hub 的接口模型在预训练里见过，文档只是重复；Hub 没见过，文档是唯一来源。

### 六、失败与恢复：可观测量与因果谨慎

4,032 条轨迹里保留 3,955 条（剔掉 77 条标注缺失或无效），用 Gemini 3 Flash 按 31 种细粒度错误标注，再合并成 6 类。合并规则在 §B.1.1 里写明，例如"参数错误"= 参数误用或参数幻觉，"执行错误"= 格式错误或代码错误，"幻觉"= 六种幻觉子类的并集。

恢复策略的分析是另一套编码：从轨迹里识别出 agent 在出错之后做了什么（重查正确值、拆解任务、原样重试、换备用方案、跳过、切换目标、查前置条件、等待、解析报错信息），然后统计"用了该策略的题"与"没用该策略的题"的分数差。这里论文自己加了免责声明：数据是观测性的，策略使用与结果之间可能被任务难度、模型能力、错误类型共同影响，因此这些数只能读成"在某模型、某测试集条件下的关联"（§B.4.1）。

### 七、开销

每次测试成本从 Grok-4.1-Fast 的 0.01 美元到 Claude-Haiku-4.5 的 0.22 美元，差 22 倍；换算成"每美元得分"是 7,489 对 224，差 33 倍。token 消耗从 128k 到 199k，差异不大，说明成本差主要来自单价而不是啰嗦程度（Table 4）。注意这里的"每次测试"是三次重复里的一次，不是一道题的全部成本。

边界有四条。第一，单轮任务，没有用户对话，因此听不出"信息不全时该不该追问"。第二，8 分钟墙钟上限会截断长任务，而 $n^*$ 最大到 24，这条上限可能改变了长任务的分数。第三，副本只保证在 $\mathcal{R}^*$ 上等价，超出这个请求集合的行为不可信。第四，闭世界不变量的严格程度取决于 $F(\tau)$ 列了什么，论文没有逐题列出。

## Ideas

### 不足

1. **每种条件只跑 3 次，二值通过率的方差被低估**（评估问题）。224 道题 × 3 次 = 672 个观测，一道题的三次结果只能是 0、1/3、2/3、1 四档。而报出的 ±2.4 是**任务级**自助区间，它回答"换一批题会怎样"，不回答"同一批题再跑三次会怎样"。对 49.3 与 38.0 这种尾部数字，运行间的抖动可能就有好几分；对 0.586/0.570 那类跨档差异（记忆那篇）也是同理。要补这一项，成本不高：把 3 次提到 10 次，或者用每题的三次结果估一个运行方差，再把它并进区间。

2. **副本保真度只有定性描述，没有量化**（系统问题）。"自动一致性测试 + 对抗探测"这两条路都写了做什么，但没写结果：108 个接口里多少通过了结构等价检查、多少有已知不一致、不一致怎么处理、有没有接口干脆没实现。而整篇论文的可信度都建立在"副本在 $\mathcal{R}^*$ 上与生产等价"这个假设上（Eq. 1）。一个可检验的替代做法是：公布每个接口的一致性测试用例数与通过率，并把已知不一致列成表。

3. **"副作用"只覆盖被建模的表，而真实企业的副作用很大一部分在表外**（系统问题）。通知、审计日志、webhook、下游同步都被明确排除，理由是 agent 看不到。但论文同时又声称能"检出对无关资源的修改或删除"（§1）——这句话的作用域是数据库行，不是"系统状态"。一个真实的事故可能是"多给一个人发了通知"，这在当前装置里完全不可见。这不算错误，但标题里的"unintended side effects"需要限定词。

4. **闭世界不变量的严格程度依赖未公开的忽略字段表**（方法问题）。$F(\tau)$ 是每道题显式声明的忽略字段（例如 `updated_at`）。如果某道题的 $F$ 列得宽，副作用就检不出来；如果列得窄，正常操作产生的非确定性字段（时间戳、自增 ID、排序键）会误判为副作用。论文没有给每道题的 $F$，也没有报告"因为忽略字段而放过多少改动"。这是判分的关键旋钮，藏在附录之外。

5. **"新颖接口"的天然实验依赖训练截止，而截止时间没有逐个核实**（评估问题）。论文说 Hub 接口在 2025 年 7 月上线，"晚于多数被评测模型的训练截止"。但被评测的九个模型里既有 2024–2025 年的开源模型，也有 2026 年的新模型，各自截止时间不同；如果某个模型的截止在 2025 年 7 月之后，它在 Hub 题上的表现就不再是"现场学习"，而是"记得"。分层报告（Table 6）按模型给出了数字，但没有按截止时间分组。

6. **文档消融缺一个中性填充对照**（方法问题）。全文档条件在 Linear 上掉 4.0 分，解释是"无关文档会挤占注意力"。但全文档同时增加了约 22,300 token 的上下文占用，而"注意力被挤占"与"上下文变长导致性能下降"是两回事。要分开它们，需要一个对照条件：塞入同样长度的、与任务无关但无害的文本（例如四个服务的使用条款）。没有这个对照，"无关文档有害"这个结论就与"长上下文有害"混在一起。

7. **错误分类由单个 LLM 裁判完成，没有人工一致性**（评估问题）。4,032 条轨迹的 31 种细粒度错误全部由 Gemini 3 Flash 标注，没有报告与人工标注的一致率，也没有报告别名冲突怎么处理。"工具使用"这一类合并了"未从工具报错恢复""前置条件不满足仍继续""查询失败当作成功"三种完全不同的病，而它占了失败的大头（平均 79.9%，GPT-6 Astra 97.0%）。这个桶越粗，能指导的改进越少。

8. **恢复策略的因果表述超出数据能支撑的范围**（方法与评估错配）。恢复策略分析是观测性的，论文自己加了免责声明，但结论段仍写"高分模型偏好自适应策略、低分模型依赖重复重试"，读起来像因果。要把它变成因果，需要干预：在同一模型上强制启用或禁用某个策略，看分数怎么动。论文没有做，这可以理解（成本高），但结论措辞应当与证据强度匹配。

9. **服务级分数混杂了操作画像与时域**（评估问题）。Linear 的平均分最高（71.4），解释是"它的接口遵循可预测的 CRUD 惯例"。但四个服务的删除类任务占比从 Linear 的 7% 到 Calendar 的 53%，时域均值从 4.6 到 5.9，这两项都会影响难度。要支持"Linear 更容易"这个判断，需要按操作画像与时域分层，或者做回归控制。论文没有做。

### 创新点

**一、把闭世界不变量写成可审计的规格，并报"未被解释的改动"这一独立指标**

- 主张：副作用不应只是一个"整题失败"的开关，而应当单独报一个数——每道题平均发生多少处未被断言解释的改动、涉及哪些实体、是否波及别的用户。这样"零容忍"仍然保留，但读者能看到"错得有多远"。
- 与原文关系：增量（原文只有二值 `clean`）+ 扩展（把 $F(\tau)$ 与断言表一起公开，让严格程度可比较）。
- 最小验证：用现成的 2,016 条轨迹重算每题"未被解释改动数"，按模型与文档条件分组，看它与 `Score` 的关系。判据是这个数与 `Score` 的秩相关显著为负，且能区分"断言少几条"与"多改了几处"两类 0 分。
- 失败条件：绝大多数任务的未被解释改动数要么为 0 要么很大（双峰），这个指标没有分辨力，那么它只适合当诊断而不适合当主指标。

**二、把领域副作用纳入模型，至少是可观测的那一类**

- 主张：通知、审计日志、webhook 是真实企业事故的主要载体，应当在副本里建模成"只追加的日志表"，并纳入差分。这样"给不该给的人发了通知"就能被检出，而不是被排除在外。
- 与原文关系：反驳（原文明确把内部副作用排除在副本之外，理由是 agent 看不到）。
- 最小验证：在 Slack 与 Linear 两个服务上实现通知表与审计表，复跑现有 224 道题，统计新增检出的副作用数与被判失败的题数变化。判据是至少 5% 的任务因此从通过变为失败。
- 失败条件：新增检出的比例低于 1%（多数任务本来就不会误发通知），说明这类副作用在实践中罕见，排除它们是合理的简化。

**三、用中性填充对照分离"无关文档"与"长上下文"**

- 主张："无关文档有害"需要与"上下文变长有害"分开。做法是加一档对照：同样长度的、与任务完全无关的文本（服务条款、随机文档），如果这一档也掉分，说明原因是长度；如果只有无关**接口规格**掉分，说明是语义干扰。
- 与原文关系：反驳（原文把 Linear 上 −4.0 直接归因于注意力被挤占，没有做这个对照）。
- 最小验证：在 57 道 Linear 题上加第四档条件（22,300 token 的服务条款），与三档现成条件配对比较。判据是两档的差值显著不为零。
- 失败条件：两档差值落在噪声内，说明长度与语义干扰无法分离，或者两者效果相同，那么"挤占注意力"这个解释应当改为"长上下文"这个更中性的说法。

**四、把判分契约反过来当训练信号，测"契约会不会被利用"**

- 主张：状态差分是一个可判定的奖励，因此可以被 agent 直接优化。需要先测它在优化下的稳健性：如果一个 agent 被告知断言的内容，它能不能用与任务意图无关的方式满足断言（例如直接往表里写行而不执行业务流程）。
- 与原文关系：正交（原文只把契约当日志，没当奖励，也没测它的可攻击性）。
- 最小验证：选 30 道题，把断言内容泄露给 agent，看它的分数与"是否走了合法业务路径"（人工判）之间的关系。判据是分数显著上升但合法路径比例下降。
- 失败条件：泄露断言后分数基本不变，说明断言已经隐含了业务语义（例如要求提交谱系），契约可以直接当奖励使用。

**五、从单轮扩到多轮，把"该不该问"纳入评测**

- 主张：企业任务的信息缺失是常态，正确行为可能是先追问而不是硬做。当前装置是单轮，因此"编造一个标识符"与"追问一个标识符"在评测上没有区别——两者都不通过，但前者危险得多。
- 与原文关系：扩展（原文明确限定单轮，作者列了 horizon 作为设计轴但没有覆盖对话）。
- 最小验证：给 40 道歧义高的题加一个可查询的"用户"，记录 agent 是否追问、追问了几轮、以及最终状态是否正确。判据是"追问后再做"的通过率显著高于"直接做"，且编造标识符的尝试率可测。
- 失败条件：追问率接近零且加了用户后通过率不变，说明这些任务的信息其实足够，歧义度这个维度的设计没有生效。

## 相关工作

与 [ThinkingBox](li2026-thinkingbox.md) 是同一族里最直接的两篇：都用环境状态而非调用轨迹当判据，都强调能检出附带损伤。差别有三点。**闭世界假设相反**：Agent-Diff 默认"没被断言解释的改动就是错"（有罪推定），ThinkingBox 默认"没写进检查的就不管"（无罪推定）。前者更严，需要任务作者穷举合法改动；后者更好写，但可能漏掉未被想到的破坏。**交互形态不同**：Agent-Diff 单轮、无用户；ThinkingBox 有模拟用户、多轮、政策约束。**服务形态不同**：Agent-Diff 复刻四个公开 SaaS 的接口，ThinkingBox 自建五个业务域的后端。

与 [Lakehouse Skills](schneider2026-lakehouse-skills.md) 共享"代码—状态同构"的前提，落点不同：那篇把每一条流水线代码映射成数据提交，用提交谱系做细粒度核对；这篇把每个 API 调用映射成实体表的一行变化，用表差分做核对。两者的严格程度都取决于"映射是否完备"：那篇的漏洞是验证器与 agent 同域（可被写出来），这篇的漏洞是忽略字段表（可被放过）。

与 [OAT](yeh2026-oat.md) 都在做失败归因，粒度不同：OAT 用成功轨迹学异常检测，给出步级的可疑分数；Agent-Diff 用 LLM 裁判把整条轨迹归到一个主导错误类，给出类级统计。前者的优势是能定位到步，后者的优势是能跨模型汇总。两者共同的弱点是标注质量：OAT 的步级标签由作者自标、无一致性统计，Agent-Diff 的错误标签由单个 LLM 裁判给出、同样没有一致性统计。

与 [SAGE](hu2026-sage.md) 同属"重设参照系"的工作，重设的参数不同：SAGE 重设的是检索基线的强度，Agent-Diff 重设的是"什么算做对了"——从"回答像不像"改成"状态对不对"。两者都依赖一个确定性信号（SAGE 用短答案匹配，Agent-Diff 用表差分），因此都把开放式判断排除在外。

与 [A-RAG](du2026-a-rag.md) 与 [DCI](li2026-dci.md) 在接口上对照：A-RAG 把检索做成三层工具，DCI 让 agent 用终端直接读语料，Agent-Diff 让 agent 用 Bash 直接调 API。三者都是"少封一层接口、多给一点自由"，区别是交互对象：语料、文件、还是带副作用的服务。

## 可复现

代码与数据：`https://github.com/agent-diff-bench/agent-diff`，MIT 许可（Abstract 末、§7）。论文给出了任务分类的五维统计（Table 3）、每个服务的题量与时域、108 个接口的服务内分布（Box 27、Slack 25、Linear 19、Calendar 37）、以及 API schema 的来源与访问日期（Table 12）。

已给出的关键设置：ReAct 外壳加 Bash 代码块；三档文档（约 400 / 3,200–10,000 / 22,300 token）；每（任务，条件）3 次重复；终止条件为 `<done>`、40 轮、8 分钟；温度用各家默认；推理走 OpenRouter；自助法 10,000 次抽样、固定种子 42；错误标注用 Gemini 3 Flash、31 类合并为 6 类。

无法复现或未给出的部分：副本保真度的量化结果（每个接口的一致性用例数与通过率）；每道题的忽略字段表 $F(\tau)$ 与断言条数；生成任务用的完整提示词只在附录 F 给了一份，两个生成模型的具体版本与温度未写；错误标注与人工的一致率；恢复策略的编码规则（哪些命令算"查正确值"、哪些算"拆解")只给了类别名。
