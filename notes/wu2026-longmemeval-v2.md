# LongMemEval-V2: Evaluating Long-Term Agent Memory Toward Experienced Colleagues

## Why

先看一个具体场景。一个 agent 在定制的 ServiceNow 系统里干了几周活：处理事件单、清理重复问题、查硬件资产。它踩过的坑包括某个筛选条件默认是 `>=` 而不是 `=`，所以按人名过滤会把别人的记录也带出来；某个字段只在问题被标记为重复、进度从"评估"改成"关闭"之后才出现。一个熟悉这套系统的同事知道这些，新来的人不知道。**记忆**要解决的正是这件事：让 agent 从过去几十上百条操作轨迹里，把"这个环境的界面长什么样、状态怎么变、常见流程有哪些、坑在哪"沉淀下来。

现有的记忆基准在这件事上都有缺口，而且缺口在机制层。第一类**对话记忆**（LoCoMo、LongMemEval-V1、PersonaMem）：上下文是用户与助手的对话，记的是"用户说过什么、偏好什么"。它们的历史长度从一万多 token 到一百多万 token，但内容同质——都是自然语言对话，噪声少、结构单一，检索器切块就能用。第二类**长上下文基准**（LongBench-V2、MemoryAgentBench）：测的是从长文档里找信息，连"跨会话持续积累"这个维度都没有。第三类**agent 轨迹记忆**（MemoryArena、AgentLongBench、EMemBench、FileGram、AMA-Bench）：开始用 agent 轨迹了，但多数只覆盖一条或少数几条轨迹内部的依赖，或者间接用下游任务成功率当记忆质量的代理。这几种做法都回答不了同一个问题：**记忆系统能不能把"环境经验"沉淀下来，而不只是把"这一条轨迹"记住**。

还有一层缺口在评测形式上。多数记忆基准的评法是"把历史塞给记忆系统，然后用下游任务成功率打分"。这个数混了三件事：记忆有没有找到证据、reader 会不会读、以及 planner 会不会用。要单独评记忆，必须把 reader 固定住、只让记忆系统负责"交出证据"；否则一个强 reader 能把弱记忆的缺陷盖住，一个弱 reader 也能把好记忆的收益抹平。

为什么现在必须解决：长期运行的 agent 正从演示走向值守——它们要在一个固定环境里反复工作，每次重启都丢掉经验就是每次从零学。而"经验"这种东西既不是用户偏好（不能靠一句"我喜欢简短回答"概括），也不是单条轨迹的细节（不能靠检索相似片段解决）：它是跨轨迹归纳出来的环境知识，包括失败的轨迹。如果评测继续只用对话历史或单条轨迹，记忆系统就会朝着"更好地检索相似对话"优化，而真实需要的是"更好地归纳环境"。

于是问题落到这里：能不能造一个基准，上下文是**几十上百条真实 web agent 轨迹**（含失败），问题只问环境经验，评法是固定 reader、只让记忆系统交证据？以及，把上下文从对话换成轨迹、从几万 token 拉到上亿 token 之后，现有的记忆方法还能不能用？

## What

论文的答案是：造出这样一个基准（LongMemEval-V2，简称 LME-V2），并把"记忆"重新定义成一个**证据收集接口**——记忆系统只提供两个 API，`Insert(轨迹)` 与 `Query(问题)`，返回一段有预算上限的多模态上下文，由一个固定的 reader 模型作答。在这个设定下，最朴素的做法只有 42.8%，一个按"状态片段"检索的 RAG 加轨迹笔记到 51.0%，专为这个任务设计的三池 RAG（AgentRunbook-R）到 58.6%，直接用现成编码 agent（Codex）到 69.9%，加了工作流指令、清单与检查脚本的编码 agent（AgentRunbook-C）到 74.9%（Table 2 的 Small 档）。同一批方法在 115M token 的 Medium 档上分别是 38.1%、45.9%、57.0%、68.7%、70.1%。

先把任务说清楚。输入是一串按顺序到达的轨迹 $H_i=\{h_{i,1},\dots,h_{i,m}\}$，每条轨迹是一次完整的 web 任务尝试——目标、起始 URL、一序列状态（截图与可访问性树）、每步的动作、最终成败。系统逐条 `Insert`，然后用问题 $q_i$ 调一次 `Query`，得到上下文 $c_i$，截断到 200K token 后交给固定 reader 作答（§3.3）。输出是答案正确率与**查询延迟**两个数。边界是四个定制 web 环境（WebArena 的 OneStopShop、CMS、Reddit，WorkArena 的 ServiceNow）、451 道人工标注题、静态预采集的轨迹序列；不含在线学习、不含端到端任务成功率、不含编程类或桌面类 agent。

### 新认识：记忆的对象从"对话"变成"环境经验"

第一个认识是**评测的上下文该换**。以前记忆基准的上下文是对话，信息密度低、噪声少、一句话就能定位；换成 agent 轨迹之后，同样的"一百万 token"里塞的是截图、DOM 片段、点击序列、报错——信息密度高、噪声大、证据分散在多个状态里。论文用一条统计说明这个差别：LME-V2 里每道题平均需要 1.4 条轨迹作证据（最少 1 条、最多 5 条），而动态与工作流类问题往往需要把一条轨迹里很多个状态拼起来才能答（§3.2）。`[已验证：§3.2、Fig. 3 右]`

第二个认识是**"五种能力"比"一种回忆"更能刻画经验**。论文把"一个有经验的同事内化了什么"拆成五项：静态状态回忆（界面有哪些元素、模块有什么能力、不同状态之间细微差别）、动态状态追踪（给定状态与动作，环境会怎么变，相当于一个世界模型）、工作流知识（常见任务要做哪几步）、环境陷阱（这个环境里反复出现的坑）、前提意识（有些假设在别的环境成立、在这里不成立）。前四项是"知道这个环境"，第五项是"知道自己可能记错"，对应到题目上就是**错误前提题**：题目描述里埋一个不成立的假设，答对的方式是指出前提错了（§3.1）。`[已验证：§3.1]`

第三个认识是**"给出证据"与"给出答案"是两种能力，要分开测**。论文做了两组试点。第一组不给任何历史，只给问题，七个前沿模型最好只有 14.1%（Kimi-K2.5），最差 2.4%（Grok-4.20），说明题目问的是环境特有知识，参数里没有。第二组给 oracle 证据：直接把含答案的轨迹喂进去，Qwen3.5-9B 只有 59.6%，GPT-5.4-mini 65.3%；但如果把证据缩成"答案状态前后各一步的窗口"再加一份策略笔记，两者分别升到 82.5% 与 86.3%；用 Codex 直接翻文件能到 89.7%（§3.4、Fig. 4）。这组数字的含义是：**原始轨迹即使全给也不够，证据需要被整理**；而"整理"这件事恰恰是记忆系统该做的。`[已验证：Fig. 4]`

### 新方法：一个最小接口 + 两个基线

第一样方法是**上下文收集式的评测协议**。记忆系统只被允许实现两个 API：`Insert(h)` 把一条轨迹写进记忆，`Query(q)` 返回一段证据上下文。评测时按顺序插入、查询一次、截断到 200K token、交给固定 reader。这个协议的作用是**把 reader 从变量里删掉**：同一道题、同一个 reader，分数差异只能来自记忆系统交出的证据。它放弃了端到端成功率这个指标，换来的是对"记忆质量"的直接测量（§3.3）。`[§3.3]`

第二样方法是**AgentRunbook-R：三池检索**。写入时从每条轨迹里抽出三类东西，分别放进三个池：原始状态片段池（以某个状态为中心、含前后动作的窗口，保留细粒度界面证据）、状态转移事件池（相邻状态之间的变化，回答"这个动作让环境怎么变了"）、流程与提示笔记池（轨迹级的可复用工作流、导航模式、环境坑）。查询时由一个 LLM 控制器读问题与记忆快照，为三个池分别生成检索查询（多个状态查询、一个事件查询、一个笔记查询），可以跳过无关的流；每路用稠密检索取回，渲染成多模态上下文（§4.1）。`[§4.1]`

第三样方法是**AgentRunbook-C：把记忆当文件系统**。写入时不做任何加工，每条轨迹直接存成文件。查询时创建一个沙箱，里面放问题、一份工作流说明（告诉 agent "你现在是记忆模块，按这几步收集证据"）、一份查询时渲染的记忆清单（概括当前有哪些轨迹，便于先缩小范围）、以及一组检查脚本（查看某个状态区间、在某条轨迹内搜索）。然后调用一个现成的编码 agent，让它写出结构化的检索结果：一段简短的记忆笔记，加若干条被选中的轨迹状态区间，渲染成上下文（§4.2）。`[§4.2]`

第四样方法是**用编码 agent 的行为做诊断**。论文解析 Codex 与 AgentRunbook-C 的事件流，把 shell 命令分成五类（读任务、按清单检索、原始轨迹探索等），比较两者的命令次数（§D.2）。这条不是方法，是把"为什么 C 更快"变成可观察的量。

### 新结论：数字、代价与成立条件

**规模。** Small 档 100 条共享轨迹、约 2.5K 个状态、25.6M token；Medium 档每题约 498 条轨迹、14.9K 个状态、114.8M token。作为参照，只给含答案的那 1.39 条轨迹是 39.3 个状态、310.8K token——也就是说 Medium 档里 99.7% 的内容与当前问题无关（Table 3 旁边的统计、Fig. 3 左）。`[已验证]`

**题目构成。** 451 道题：静态 211（46.8%）、动态 66（14.6%）、工作流 83（18.4%）、陷阱 91（20.2%）。来源域以 WebArena-OneStopShop 最多（134 题，29.7%），ServiceNow 55 题（12.2%）。格式上多选 69（15.3%）、短答 226（50.1%）、自由作答 156（34.6%）（Fig. 2）。`[已验证；这张环形图的读数是从 PDF 文本重建的，见可复现]`

**主结果（Small 档）。** 不给记忆 0.013；按状态片段检索 0.428；加笔记 0.510；AgentRunbook-R 0.586（延迟 26.9 秒）；Codex 0.699（177.2 秒）；AgentRunbook-C 0.749（108.3 秒）（Table 2）。Medium 档对应 0.013、0.381、0.459、0.570（25.8 秒）、0.687（185.8 秒）、0.701（139.9 秒）。`[已验证]`

**消融。** R 的三个池里，去掉原始状态片段池掉得最多：Small 从 0.586 掉到 0.423，其中静态题从 0.661 掉到 0.286；去掉事件池掉到 0.556（动态 0.559、陷阱 0.276）；去掉笔记池只掉 0.007。C 的三个脚手架里，去掉工作流说明掉得最多（0.749→0.701，Medium 0.701→0.641），去掉记忆清单主要影响延迟（0.749→0.747，但 Small 延迟从 108.3 秒涨到 155.0 秒、Medium 从 139.9 涨到 211.6 秒），去掉检查脚本的结果不一致（Small 0.714，Medium 0.718）（Table 2）。`[已验证]`

**代价。** 查询延迟从 0.1 秒（朴素 RAG）到 185.8 秒（Codex）。Medium 档的编码 agent 方法都在 2 分钟以上，延迟测量时把并发查询限制在 3 个进程以避免压垮磁盘（§C）。`[已验证]`

## How

判型：以**实证与基准类**为主，附**系统与算法类**。实证与基准类的依据是核心产出是 451 道人工标注题、两档 haystack、一套评测协议；系统与算法类是两个基线方法（三池检索、文件式编码 agent）与它们的脚手架。没有新模型、没有训练，所以不能按算法类要求它做大规模消融。

### 一、轨迹怎么来，题目怎么标

轨迹取自 WebArena 的 OneStopShop、CMS、Reddit 与 WorkArena/WorkArena++ 的 ServiceNow，用 AgentLab 的统一状态表示与 ReAct 风格的基础 agent 采集，模型是 Codex，用 GPT-5.2 与 GPT-5-mini 做拒绝采样。最终池子 1,540 条（WebArena 599、WorkArena 941），成功率 52.0%，每条平均 28.1 个状态（§3.2）。

标注四步。第一步收集轨迹。第二步写题：人工先读轨迹，找出"一个有经验的同事会自然学到的东西"，再筛到"强模型不看历史答不对"——论文报告的做法是人工测了 Gemini-3-Pro、GPT-5.2、Grok-4.1-thinking、Claude-Opus-4.6 四个模型，保证至少两个答错（脚注 3）。陷阱类题的问法特殊：给一张截图加一句话，模拟"没经验的新同事来问"。第三类是错误前提题，在已有的静态、动态、工作流题上改写，把假设改成错的（§3.2）。

第三步标"答案轨迹"。先由人工给每道题标一小组含答案的轨迹，再用 Codex 生成初稿、人工核验，目的是把每道题的**全部**含答案轨迹都找出来。第四步造 haystack。Small 档是让所有题共享 100 条轨迹，构造时要在"所有题一起"的前提下最小化含答案轨迹的数量——这是一个集合覆盖式的构造；Medium 档按每道题取约 500 条（§A.4）。两档都保持成功与失败轨迹的比例均衡，而且很多题只能从失败轨迹里得到答案（§3.2）。

### 二、为什么必须用"证据窗口"才能读懂轨迹

试点里有一个反直觉的结果：把含答案的整条轨迹全给 reader，Qwen3.5-9B 只有 59.6%；把证据换成"答案状态前后各一步"的窗口，再加一份从这条轨迹提炼的策略笔记，同一个 reader 升到 82.5%（§3.4）。差别的来源不是信息量——整条轨迹的信息严格更多——而是**信噪比与长度**：一条轨迹平均 28 个状态、每个状态带截图，整条塞进去会超出窗口或把关键状态挤到远处。这个结果直接支撑了两个基线方法的设计取向：R 走"写入时压缩"，C 走"查询时按需取"。

### 三、R 的三个池与一个控制器

写入时，对每条轨迹做三件事。切状态窗口：以每个状态为中心，取前后若干步，保留截图与可访问性树片段。抽状态转移事件：对每对相邻状态，让模型描述"这个动作之后环境发生了什么变化"——新页面、展开的面板、变化的字段、出现的确认信号、被挡住的操作。生成笔记：从整条轨迹里提炼可复用的流程与坑（提示词在 §C 的表 9，系统提示明确要求"只用给定的目标、结果、思考、动作与截图，不要发明没见过的字段或结果"）。

查询时，一个 LLM 控制器读问题与"记忆快照"，生成查询：多个状态查询（精确界面证据）、一个事件查询（关键状态变化）、一个笔记查询（程序性知识），可以跳过无关的流。三路各用稠密检索取回，渲染成多模态上下文。

三个池的作用在消融里分得很清楚：状态池负责"界面长什么样"（静态题 0.661→0.286），事件池负责"动作怎么改变环境"（动态题与陷阱题掉得最多），笔记池负责"流程"（去掉只掉 0.007，说明在这个基准上流程知识已经能从状态与事件里拼出来）。

### 四、C 的三个脚手架

C 的写入是零加工：每条轨迹一个文件。查询时创建沙箱，放四样东西——问题、工作流说明、记忆清单、检查脚本。工作流说明规定"你是记忆模块，按这几步收集证据，输出一段笔记加若干状态区间"。记忆清单是查询时渲染的摘要，让 agent 先缩小范围再细看。检查脚本暴露常用操作，例如"看某个状态区间""在某条轨迹内搜索"。

消融显示三者的角色不同：工作流说明是**正确性**的主要来源（去掉它掉得最多），清单主要是**效率**（去掉它延迟涨 40% 以上、准确率几乎不变），检查脚本是**混合**（Small 掉 0.035、Medium 反而涨 0.017，说明它有时帮着走得快、有时把 agent 引到错的方向）。

### 五、走一遍：一道"筛选条件默认是 >=" 的题

题目是"在硬件资产列表里按 `Assigned to` 搜 `Chelsea-Cynthia Tran-Dyer`，结果里还是出现别的员工，最可能的解释是什么"，正确答案是"这个系统的比较条件默认是 `>=`，所以包含其它员工"（Fig. 1 第四行）。

R 的处理：控制器判断这是一道"陷阱"题，生成一个事件查询（"筛选动作之后列表怎么变"）与一个笔记查询（"这个界面的筛选默认值"），跳过状态查询；笔记池里可能正好有一条从某次失败轨迹提炼的"筛选条件默认是 >="，事件池里可能有一条"改了比较运算符之后结果集缩小"。

C 的处理：agent 先读记忆清单，按关键词（"Assigned to"、"筛选"、"比较"）挑出三到五条候选轨迹，用检查脚本在每条里搜 `Assigned`，定位到两个状态，读前后窗口，确认界面上比较运算符下拉框的默认值，然后写一段笔记与两段状态区间作为证据。

两种路径的差别就是这篇论文的核心对比：R 在写入时就把"该怎么找"想好了，所以快；C 在查询时才想，所以慢但能处理更细的证据。

### 六、指标与它的边界

主指标是答案正确率：结构化答案（多选、短答、是非）用归一化字符串匹配，自由作答与陷阱题用 LLM 判分（GPT-5.2，中等推理强度；判分提示词在 §C 表 5）。陷阱题的判分规则很细：只有明确识别出前提错误、且结论与参考答案等价才给 1；给一个"跟着错误前提走"的具体答案给 0；只回"不知道"而不指出错误也给 0；既否定前提又给出具体答案（自相矛盾）给 0。

第二个指标是查询延迟，测量时限制并发为 3 个进程。没有报告写入延迟与写入成本——这一点在 Ideas 第三条展开。

### 七、开销与边界

查询侧的代价从 0.1 秒到 186 秒。Small 档的 haystack 只有 25.6M token，Medium 是 115M——后者是前者的 4.5 倍，但所有方法的准确率都**下降**（例如 C 从 0.749 掉到 0.701），说明多出来的 90M token 主要是干扰而不是信息。写入侧：R 对每条轨迹都要调模型生成事件与笔记，成本与轨迹数成正比；C 只写文件。论文没有报这两项的时间与金额。

边界有四条，作者在 Limitations 里列了三条：只覆盖 web agent（不含编程、桌面、企业专有 agent），用预采集轨迹而不是在线学习（因此测不到"agent 自身行为变化带来的分布漂移"），上下文收集式评测不直接等价于端到端成功率。第四条是本文自己的判断：Small 档所有题共享同一个 haystack，题目之间因此不独立，跨题比较的统计意义有限。

## Ideas

### 不足

1. **两个基线换了控制器，主结论因此混合了两个变量**（方法问题）。AgentRunbook-R 的控制器是 Qwen3.5-9B（与 reader 同模型），AgentRunbook-C 的控制器是 GPT-5.4-mini（xhigh 推理），Codex 基线也是 GPT-5.4-mini。于是"0.586 → 0.749"这个提升同时包含了三件事：检索机制从三池换成文件、控制器从 9B 换成更强的模型、以及多了三个脚手架。论文在 C 内部做了脚手架消融，但没有做"同一控制器下的 R 与 C"这一格，也没有做"Qwen3.5-9B 当控制器翻文件"这一格。缺了这两格，就无法回答"文件式记忆本身有多好"。

2. **摘要的数字是两档的算术平均，其中一个对不上**（评估问题）。摘要写 40.1%、57.8%、69.3%、72.5%、182 秒、6.9 倍、快 32%。按 Table 2 逐项复算：57.8 是 0.586 与 0.570 的平均，69.3 是 0.699 与 0.687 的平均，72.5 是 0.749 与 0.701 的平均，182 是 177.2 与 185.8 的平均，6.9 倍是 181.5 ÷ 26.35，快 32% 是 1 − 124.1 ÷ 181.5。只有 40.1 对不上：0.428 与 0.381 的平均是 40.45。差异不大，但摘要与表格的聚合口径没有说明（是两档平均还是别的加权），引用时容易把一个两档平均当成单档成绩。

3. **只报查询延迟，不报写入成本**（方法与评估错配）。这是全文最大的口径缺口。R 在写入时要为**每条轨迹的每一对相邻状态**生成事件、为每条轨迹生成笔记，成本与轨迹数乘状态数成正比；C 只写文件。Medium 档是 498 条轨迹、14.9K 个状态，R 的写入开销比 C 大一个量级以上。只报查询延迟，等于把"记忆"的账只算了一半，而"建库贵还是查询贵"恰恰是选型时最关键的一项——同一批作者在另一篇记忆评测里把这件事做成了四段式账本，这篇没有沿用。

4. **宣称五种能力，主表只报四列**（评估问题）。题目构成里有 46.8% 静态、14.6% 动态、18.4% 工作流、20.2% 陷阱，另有建立在静态、动态、工作流之上的**错误前提题**——第五种能力"前提意识"在 Table 2 里没有单独一列。它只出现在附录 D 的错误构成图里，作为一个误差类型。也就是说，论文最想区分的那一项能力（"知道自己可能记错"）没有主结果；而这一项又恰好是 R 与 C 差别最大的地方（§D.1 说 R 不改善弃答，因为它把证据直接摆出来，reader 反而被误导；C 因为被要求显式指出前提不一致而变好）。

5. **Table 2 没有置信区间，且只跑一遍**（评估问题）。451 道题、单次运行，0.586 与 0.570 这样的跨档差异、0.749 与 0.747 这样的消融差异，都没有方差。论文对 R 与 C 的主提升用了配对自助检验（表注里标了星号），但消融行的差异没有标，而消融的结论（"清单主要影响效率"）恰恰建立在一个 0.002 的差上。

6. **haystack 的构造方式在替记忆系统降难度**（数据问题）。Small 档的"最小答案核心"是一个集合覆盖式的构造：在 100 条共享轨迹里，让**每道题**都至少有一条含答案轨迹，同时让含答案轨迹的总数尽量少。这会让证据更集中，而不是更分散。Medium 档按题取约 500 条，虽然稀疏性更强，但抽样时同样要保证答案在池子里。真实环境里"答案恰好被记录过"并不是保证成立的；这个基准测的是"能不能在已记录的证据里找到"，不是"证据不存在时能不能判断"（后者只有陷阱题覆盖一小部分）。

7. **判分模型与被测模型重叠**（评估问题）。自由作答与陷阱题的判分用 GPT-5.2，而 GPT-5.2 同时是被试模型之一（无上下文时 4.7%）。更关键的是陷阱题的判分规则里有一条"模型明确说自己无法访问用户的具体实时环境/配置，因此无法验证，也可给 1"——这条规则把"回避"也算对，可能高估陷阱题的正确率。论文没有报判分与人工的一致率。

8. **环境是公开基准，存在被模型见过的可能**（数据问题）。WebArena 与 WorkArena 是公开环境，模型可能从训练数据里见过界面结构。论文用"无上下文时最高 14.1%"来论证参数知识不够，这个证据是有效的；但 14.1% 与随机猜（四选一 25%）相比并不高，说明题目设计确实避开了"靠常识能猜对"，同时也意味着"见过的环境知识"在多数题上不足以直接答对——这是一条正面证据，不是问题。真正的问题是：如果模型部分记得这些环境，那么不同模型之间的比较会偏向"更可能见过该环境"的模型，而这个偏差没有测。

### 创新点

**一、把记忆评测钉在"证据接口"上，并给出可复现的固定 reader 协议**

- 主张：记忆系统的能力应当用"交出的证据能不能支撑正确答案"来测，而不是用端到端成功率。只要固定 reader、固定上下文预算、固定插入顺序，不同记忆系统就在同一个坐标系里可比，且这个协议可以被复用到任何新环境。
- 与原文关系：增量（原文提出了这个协议并实现了一版）+ 扩展（把协议写成可迁移的规格：两个 API、一个预算、一个固定 reader，并规定必须同时报写入成本）。
- 最小验证：把同一协议套到第二个领域（例如一个内部工单系统或一个代码仓库的提交历史），用同一 reader，检查方法的相对排序是否保持。判据是排序的 Kendall τ 高于 0.7。
- 失败条件：换领域后排序大幅变化（τ 低于 0.5），说明协议没有抓住记忆的共性能力，只是这个环境的特化，可迁移性主张不成立。

**二、把写入成本做成一等指标，给出"建库 vs 查询"的账本**

- 主张：任何记忆方法都应该报四个数——每条轨迹的写入时间与 token、每次查询的延迟与 token。只报查询延迟，等于把方法选择中最贵的那一半藏起来。
- 与原文关系：反驳（原文只报查询延迟，而 R 与 C 的写入成本差一个量级）。
- 最小验证：在 Small 与 Medium 两档上补测 R 与 C 的写入时间与 token（R 要为每对相邻状态生成事件，C 只写文件），算出"总成本 = 写入 × 轨迹数 + 查询 × 题数"，看两条准确率—总成本曲线是否交叉。
- 失败条件：把写入成本算进来后两条曲线仍然平行（C 在所有预算下都优于 R），说明写入开销不影响选型，缺这一项只是报告不全而非结论错误。

**三、在匹配控制器下重做 R 与 C 的对比**

- 主张：现在的"文件式记忆更好"混合了机制与控制器。用同一个控制器（例如都用 Qwen3.5-9B，或都用 GPT-5.4-mini）分别跑三池检索与文件检索，才能把"表示形式"的贡献单独量出来。
- 与原文关系：正交（补一个原文缺失的对照格）。
- 最小验证：2×2 设计——控制器 ∈ {Qwen3.5-9B, GPT-5.4-mini} × 记忆形式 ∈ {三池检索, 文件}。判据是"文件 vs 三池"的主效应在控制控制器后仍显著。
- 失败条件：主效应消失、只剩控制器的主效应，说明提升来自更强的模型而不是文件式记忆，原文的方法定位需要改写。

**四、把"前提意识"变成主表的一列，并加"证据不存在"的题**

- 主张：五种能力应当各有独立分数，尤其"知道自己可能记错"这一项——它与"检索到更多证据"是相反的：证据越多、越容易被错误前提带走。同时应当增加一类"历史里根本没有答案"的题，正确行为是明确说不知道。
- 与原文关系：扩展（原文有陷阱题，但没有单独报分；"证据不存在"的情形只被间接覆盖）。
- 最小验证：把现有 451 道题里属于错误前提的子集单独报分，并新造 50 道"历史无答案"的题（由标注者确认答案轨迹为空），比较各方法在这两组的分数与"证据越多越差"的斜率。
- 失败条件：前提意识分数与总体分数高度一致（相关高于 0.9），说明它不是一个独立能力，单独报分没有信息量。

**五、测"增量写入"与"证据过期"**

- 主张：真实 agent 是边干边学，记忆是边写边读；而且环境会变（界面改版、政策更新），旧证据会过期。现在的基准是"先插完再查一次"，测不到增量插入与冲突覆盖。
- 与原文关系：扩展（作者把"在线学习"列为未来工作，但增量写入与过期是两个更小、更可测的切口）。
- 最小验证：把 Medium 档改成流式协议——每插入 50 条轨迹就查一次题，记录准确率随插入量的曲线；再造一组"环境改版"的题（同一界面在两个时间点有两种布局），正确答案是采用较新的版本。判据是现有方法在流式协议下准确率显著低于批量协议，且在"改版"题上大量采用旧证据。
- 失败条件：流式与批量协议的准确率差异小于噪声，说明"先插完再查"不影响结论，那么这个方向只是工程优化而非评测缺口。

## 相关工作

与 [Memory Tax](he2026-memory-tax.md) 同属"重设记忆评测口径"的工作，切口相反：Memory Tax 质疑"建记忆是否划算"，把成本拆成建库、维护、推理三段；LME-V2 不问划不划算，而是把记忆的**输入**从对话换成 agent 轨迹、把**输出**从答案换成证据。两篇合起来正好补上彼此的缺口——LME-V2 缺成本账本，Memory Tax 缺"轨迹型上下文"这一档。

与 [RAW-RAG](bao2026-raw-rag.md) 的关系是"朴素基线到底有多强"。RAW-RAG 的结论是"配好的原始历史检索能打赢多数记忆系统"；LME-V2 里最朴素的"按状态片段检索"只有 0.428，加上"轨迹笔记"到 0.510，离最好的 0.749 还有距离。差异的来源是上下文形态：对话历史切块后每块自足，轨迹切窗口后需要跨状态拼接，朴素检索的收益因此下降。这不推翻 RAW-RAG，但说明它的结论有适用边界。

与 [T-Mem](guo2026-t-mem.md) 都在做"写入时组织、查询时用"，组织方式不同：T-Mem 用带类型的记忆与触发器索引，把"什么时候该想起什么"编码进索引；AgentRunbook-R 用三个池分开粒度（状态、事件、笔记），AgentRunbook-C 干脆不组织、把组织推到查询时。三种取向的差别在成本：T-Mem 与 R 都在写入时付费，C 在查询时付费（每次查询 108 到 140 秒）。

与 [Jev-Mem](jiang2026-jev-mem.md) 的关系在控制层：Jev-Mem 用一个轻量判断器决定"要不要查、查哪条线、查多深"，把成本压在控制上；AgentRunbook-R 的控制器只生成检索查询、不做预算分配，C 则完全交给一个通用编码 agent 自己决定。三者的共同问题都是"控制器由谁当"，而 LME-V2 的结果（同一批文件，换控制器就可能换分数）恰好说明这个变量的权重可能被低估。

与 [A-RAG](du2026-a-rag.md) 与 [DCI](li2026-dci.md) 在接口上呼应：A-RAG 把检索做成三层工具接口，DCI 去掉检索器、直接用终端读原始语料；AgentRunbook-C 是同一思路在记忆上的版本——不建索引，把轨迹当文件，用编码 agent 的搜索能力替代向量检索。LME-V2 给这条路线提供了一个正面的数字：文件式加脚手架 0.749，高于三池检索的 0.586。
